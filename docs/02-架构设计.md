# PerchReader 架构设计（iOS 阶段）

> 前置约束（实测得出，见 `03-环境与验证矩阵.md`）：开发机是 Linux。为了让绝大部分逻辑能在 Linux 上编译与测试，
> **Rust 核心必须是"纯 Rust、零 C 依赖"**（否则 `cargo check --target aarch64-apple-ios` 与 staticlib 交叉构建会失败）。
> 这条约束不是洁癖，而是"没有 Mac 也能推进"的技术前提，直接决定了下面若干选型。

## 一、分层

```
┌───────────────────────────────────────────────────────────┐
│ 表现层  Flutter (Dart)：iOS / Android / Web / macOS       │
│  书库网格 · 阅读器容器 · 设置 · 搜索 · 标注列表           │
├───────────────────────────────────────────────────────────┤
│ iOS 服务层（Swift）                                       │
│  ImportService   SyncService   StoreService   ReaderKit   │
│   —— 文件 I/O、后台任务、网络、生命周期、PDFKit 文本      │
├───────────────────────────────────────────────────────────┤
│ FFI 边界（flutter_rust_bridge 生成，勿手改）               │
│  Rust ↔ Dart 绑定（frb_generated.*）                       │
├───────────────────────────────────────────────────────────┤
│ Rust 核心（纯逻辑，可在 Linux 全量测试）                  │
│  model · epub · txt · pdf(结构) · index · sync · crypto   │
└───────────────────────────────────────────────────────────┘
```

**边界原则**：Rust 侧**不做网络、不做 UI、不直接持久化**；它做的是"纯计算"——解析、Locator 换算、分页、分词、索引、合并。凡是需要平台能力（URLSession、PDFKit、SQLite、后台任务）的，一律通过 Swift 服务层注入。

## 三、跨语言契约规则（flutter_rust_bridge 2.13）

1. **数据结构用 `Record` / `Enum`**（值传递），**有状态对象用 `Object`**（句柄传递）。不要用 `Box<dyn Trait>` 跨边界。
2. **错误统一为枚举 + 稳定的 `code` 字符串**（见 `perch-model::ModelError::code`），Dart 侧可 `switch`，不要抛不透明字符串。
3. **大字节流不过 FFI**。传文件路径或句柄 + 偏移量，Swift 自己去读。EPUB 内部资源同理：Rust 给 `(href, byte_offset, len)`，Swift 去读文件。
4. **所有导出函数幂等、可重入、无全局可变状态**。并发由 Dart 侧的 `Isolate` / `compute` 承担；核心保持同步纯函数，便于测试。
5. **不为 iOS 定制核心 API**。禁止在核心出现 `URL`、`Data`、`Foundation` 概念。
6. **Locator 的 JSON 结构与 Readium 的 Locator 对齐**（`href` + `locations{partialCfi, progression, position, totalProgression, cssSelector}` + `text{before, highlight, after}`），使 Readium（Swift/Kotlin/JS 三套工具链）↔ Rust 的互转近乎字段拷贝。

## 四、统一 Locator（本项目最关键的数据结构）

设计目标是"一个字符串 + 一段 JSON 能唯一确定三端三格式的任意位置"，并且在其中**附带足够上下文用于容错重定位**。

```
Locator {
  // 定位本体
  v:                u8,            // 版本，为将来演进留口
  href:             string,        // 资源标识：EPUB 为章节路径；PDF/TXT 为常量 "pdf:"/"txt:"
  type:             enum { Epub, Pdf, Txt },

  // 格式相关（互斥使用，皆可为空）
  cfi:              ?string,       // EPUB：精确锚点
  pdf_page:         ?u32,          // PDF：页号（0 基）
  pdf_rect:         ?[f32; 4],     // PDF：归一化 [x, y, w, h]（0.0~1.0，相对页面）
  txt_offset:       ?u64,          // TXT：字符偏移
  txt_byte_offset:  ?u64,          // TXT：字节偏移（解码后映射）

  // 通用进度（跨端同步的"粗粒度"真理）
  progression:      f64,           // 0.0 ~ 1.0，本书内进度
  total_progression:?f64,          // 全书进度（含前言/后记）

  // 容错重定位上下文（换文件/换版本/重排后靠这个兜底）
  text_before:      ?string,       // 位置前 N 字符
  text_after:       ?string,       // 位置后 N 字符
  text_highlight:   ?string,       // 被标注的原文
  chapter_title:    ?string,       // 所在章节标题
  chapter_index:    ?u32,          // 章节序号

  // 元数据
  created_at:       Timestamp,
  modified_at:      Timestamp,
}
```

**为什么带 `text_before/after`**：EPUB 换版本、字号重排、或 CFI 因 DOM 变化失效时，纯 CFI 定位会漂移。有了前后文，可以用"模糊匹配 + 位置提示"二次定位。这是"标注不漂移"的实现基础（M4）。

**范围标注**：由两个 Locator 组成（`start` + `end`），而不是自定义区间类型——这样单点定位与范围定位共用同一套同步与重定位逻辑。

## 五、三格式的进度映射

| 格式 | 精确定位 | 粗粒度 | 失效兜底 |
|---|---|---|---|
| EPUB | CFI（`/6/4[chap01]!/4/2/2:12`） | `progression` + 章节序号 | `text_before/after` 模糊匹配 |
| PDF | 页码 + 归一化矩形 | 页码 / 总页数 | 页码直接兜底（PDF 稳定） |
| TXT | 字符偏移 | 偏移 / 总字符数 | 偏移 + 前后文校验 |

**Rust 负责的部分**：EPUB 的 `(href, 字节偏移) ↔ CFI` 双向换算；TXT 的 `字符偏移 ↔ 字节偏移`；PDF 的坐标归一化。这些都是纯计算，**Linux 上可全量单测**。

## 六、导入管线（三阶段状态机）

```
        ┌─────────────┐
        │ registered  │  ① 前景：复制文件 + 指纹 + 插行（不解析）
        └──────┬──────┘
               │ 指纹去重通过
        ┌──────▼──────┐
        │  refining   │  ② 后台：元数据/封面/目录/字数
        └──────┬──────┘
               │
        ┌──────▼──────┐
        │  indexing   │  ③ 后台：全文倒排 + 前缀
        └──────┬──────┘
               │
        ┌──────▼──────┐
        │    ready    │
        └─────────────┘
     任何阶段失败 → failed（可重试）；每阶段幂等
```

- **幂等键**：文件指纹（`size + 首块哈希 + 尾块哈希`）。任何阶段崩溃重启后都能从指纹恢复。
- **① 阶段是"1000 本 <10s"的全部秘密**：只做 I/O + 一行插入。这是性能红线，不能被后续功能侵蚀。
- **② ③ 是"延迟索引"**：可以暂停、可以慢、可以让位给前台。
- 调度：`BGProcessingTask`（系统空闲时）+ 前台抑制（用户正在读书时不跑重活）+ 热状态降级。

## 七、存储

**问题**：iOS 侧的持久化用谁？
- `rusqlite`（bundled）= 编译 C 的 SQLite → **破坏 Linux 交叉构建**（违反前置约束）。
- 纯 Rust `redb` 4.4 → 可在 Linux 全测，但会脱离 iOS 生态（File Protection、CloudKit、系统备份策略）。

**建议（待你拍板，见待决问题 #3）**
- **Rust 定义 `Storage` port（trait），不实现具体持久化**。上层的"纯计算"函数只接受数据、返回数据。
- iOS 侧用 **GRDB（Swift/SQLite）** 实现：迁移、索引、事务、加密（`SQLCipher` 后续可选）都在 Swift 侧，符合 iOS 习惯。
- Rust 侧提供**内存实现**用于测试；未来的桌面/Android 各自实现。
- 例外：**全文索引文件**可以用 Rust 直接管（纯 Rust 写入自有格式），因为它不是"关系数据"，且能在 Linux 基准测试里复现。

**表结构草案**

```sql
books(id, title, author, format, path, size, fingerprint,
      state, cover_path, toc_json, word_count,
      progress_locator_json, added_at, last_opened_at, deleted_at)
book_resources(book_id, href, media_type, byte_len, index_state)
annotations(id, book_id, kind, start_locator_json, end_locator_json,
            color, note, excerpt, created_at, modified_at, hlc, deleted)
sync_outbox(id, entity, entity_id, op, payload_json, hlc, retry_count)
sync_state(key, hlc_wall, hlc_counter, last_pull_cursor)
```

`deleted` 与 `deleted_at` 是**墓碑**，同步完成后才能物理清除。

## 七点五、已确认事实：Readium 不生成 CFI

（来源：`docs/09-技术考证报告.md` §C.3，逐文件 grep 核对）

`readium/swift-toolkit@3.11.0` 与 `readium/kotlin-toolkit@develop` 的 **reflowable EPUB
路径完全不生成 CFI**：`readium-reflowable.js`、`EPUBNavigatorViewModel.swift`、
`EpubNavigatorFragment.kt`、`Locator.kt` 里 "cfi" 命中数均为 **0**。Swift 侧产出的
是 `cssSelector` 与 `progression`。

**影响**：

1. iOS/Kotlin 上 Readium **不会跟我们的 CFI 打架**——不存在"两边格式不一致"，
   只存在"我们写进去、Readium 读不读"。
2. **跨端 CFI 的权威版本就是我们的 Rust 实现**（`core/perch-epub/src/cfi.rs`），
   这比原先设想的"要对齐上游"更可控。
3. 真正需要担心的是**其他阅读器**（Apple Books / Calibre）导出的 CFI 导入时的兼容性。

`partialCfi` 的口径按上游契约固定为：**`!` 右侧的片段，不含 spine 引用、不含
`epubcfi()` 包装**（例：`/4/2`）。

## 八、同步设计

- **HLC（混合逻辑时钟）**：`(wall_ms, counter, device_id)`，解决"设备时钟不准"下的因果顺序。
- **进度合并**：字段级 LWW（按 HLC）。产品规则（"最远位置" vs "最后位置"）待定，见待决问题 #5。
- **标注合并**：每条标注独立 UUID，字段级 LWW，删除即墓碑。范围标注的两端**作为一条记录整体合并**（避免出现"起点是新的、终点是旧的"这种撕裂）。
- **冲突定义**：被丢弃的字段级变更 / 总字段级变更。目标 <1%。
- **收敛性验证**：给定一组并发操作，任意应用顺序 → 最终状态一致。**这是纯函数性质，可以用 `proptest` 在 Linux 上随机生成上万组场景断言**。这是"同步准"最有价值的自动化保障。

### 八点五、同步传输协议 v1（已实现于 `perch-sync::wire`）

**状态型同步，不是操作日志。** 每个 `(书, 标注)` 组合是一个 LWW 寄存器，
日志里只保留**当前胜者**，不保留历史。取舍：

| | 状态型（本项目） | 操作日志（CRDT oplog） |
|---|---|---|
| 数据量 | 与离线时长**无关** | 随离线时长线性增长 |
| 离线三个月后重连 | 只传当前值 | 要回放三个月的历史 |
| 撤销历史 / 挑旧版本 | **做不到** | 可以 |

阅读器的同步对象是"当前进度""当前标注集合"，不是编辑历史，所以选状态型。

**变更（Change）的 JSON 形状**

```jsonc
// 进度
{ "book": "<uuid>", "hlc": "1700000000000-0-iphone",
  "op": "set", "value": { "kind": "progress", "locator": { … } } }

// 标注（整条搬运，范围标注两端不会撕裂）
{ "book": "<uuid>", "annotation": "<uuid>", "hlc": "1700000000001-0-ipad",
  "op": "set", "value": { "kind": "annotation", "annotation": { … } } }

// 删除（墓碑只带时间戳，不带正文——墓碑要比正文活得久）
{ "book": "<uuid>", "annotation": "<uuid>", "hlc": "…", "op": "tombstone" }
```

- `annotation` 缺省 ⇒ 目标是**这本书的进度**；有值 ⇒ 目标是**该条标注**。这一个字段
  就决定了寄存器身份。
- `hlc` 是**线上唯一的排序依据**，用文本形式（`{wall_ms}-{counter}-{device}`），
  与 `Hlc` 的 `Display`/`parse` 一致，不另立第二套二进制布局。
- 标注自身也带 `hlc` 字段（本地存储用）。若两端都填了就必须一致，
  否则报 `SYNC_INCONSISTENT` —— 不允许出现"两个时间戳"这种迟早出事的状态。

**一次往返完成双向同步**（弱网下比 push/pull 两趟更省）：

```jsonc
// 请求：推上去本地变更，顺便拉 since 之后的增量
{ "protocol": 1, "device": "iphone", "since": "1700000000000-0-ipad",
  "limit": 500, "changes": [ … ] }

// 响应：本页增量 + 新游标 + 服务端对本次上传的处理统计
{ "protocol": 1, "changes": [ … ], "nextCursor": "…", "hasMore": false,
  "stats": { "initialized": 0, "updated": 3, "staleIgnored": 1,
             "conflicts": 0, "unchanged": 12 } }
```

**增量游标**：服务端返回 **HLC 严格大于 `since`** 的寄存器。因为 HLC 是全序且唯一的
`(wall, counter, device)`，这个游标不漏也不重（有测试逐页走完全集校验）。
分页大小默认 500。

**版本协商**：接收方接受 `收到版本 <= 本端版本`（旧客户端能连新服务端），
拒绝更高版本（不认识就无法降级），`0` 视为非法。

**编码**：v1 用 JSON。传输层只认字节序列，HTTP / WebSocket / 文件同步都不影响本模块；
将来换二进制编码只需替换 `to_json`/`from_json`，数据结构不动。

**已知限制（诚实标注）**
- 无撤销历史（见上表）
- 服务端本身**尚未实现**：本仓库只有协议类型 + 客户端/服务端的**共同逻辑**
  （`ChangeLog` 既是客户端状态也是服务端状态）
- 冲突率口径固定为 `conflicts / total_changes`，`Unchanged` 不稀释分母

## 九、性能预算（把目标翻译成可执行约束）

| 指标 | 预算 | 实现约束 |
|---|---|---|
| 打开 <1s | 首屏可交互 | 打开路径禁止建索引/生成封面/解析全篇 |
| 翻页 60fps | 帧 <16.7ms | EPUB 单页 DOM 大小可控；不重建 WebView；预加载相邻资源 |
| 1000 本 <10s | 登记阶段 | 只 I/O + 插行；批量事务提交 |
| 内存峰值 <300MB | 长时阅读 | 索引分片落盘；图片按需解码 |
| 崩溃率 <0.1% | 生产 | 核心不 panic：所有可预期错误 → `Result`；`unwrap` 在 CI 里禁（clippy 规则） |
| 冲突率 <1% | 同步 | 单条标注独立合并；字段级 LWW；范围标注原子合并 |
