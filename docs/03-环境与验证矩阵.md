**为什么用 rustup 而不是 pacman 的 rust**：
1. 需要 iOS target（`rust-std-aarch64-apple-ios`）——pacman 的 rust 装不了；
2. 系统的 `rustc` 当前是**坏的**（见 §三），rustup 版本可绕过；
3. 不触碰系统包，随时可回退。

**PATH 优先级**：`~/.config/fish/conf.d/rustup.fish` 把 `~/.cargo/bin` 放在 `$PATH` 最前（fish 每次启动生效）；`~/.bashrc` 也加了一行兼容。

### 2.3 CachyOS 源：**没有可用的国内镜像**（已实测，别在这上面花时间了）

- `mirrors.ustc.edu.cn/cachyos/` 只镜像了 ISO / keyring / mirrorlist，**repo 数据库文件全部 404**
  （`/cachyos/repo/x86_64_v4/` 目录存在但 `cachyos*.db` 取不到；`/cachyos/repo/znver4/` 亦然）
- `mirror.sjtu.edu.cn/cachyos/`、`mirrors.tuna.tsinghua.edu.cn/cachyos/` → **404**（完全不镜像）
- 现有配置里的 `mirror.krfoss.org`、`cdn.lansing2600.org` 从本机访问返回 **418**（反爬/地域限制）

**结论**：CachyOS 仓库暂时只能走原有国外源。这不影响本项目（项目只在 `core/` 里用 cargo，且 cargo 已走 USTC）。
如果以后要更新系统，建议用你的 `proxy_on` 开代理再 `shelly upgrade-all`。

## 三、⚠️ 本机系统 `rustc` 是坏的（已隔离，但你需要知道）

```
$ rustc --version
rustc: symbol lookup error: /usr/lib/librustc_driver-b9ead9e03832c46d.so:
undefined symbol: _ZNSt7__cxx1112basic_stringIcSt11char_traitsIcESaIcEE9_M_mutateEmmPKcm, version LLVM_23.1
```

**根因（已定位）**
- 系统 `rust` 包：`1.99.0-1`，构建日期 **2026-10-01**
- 当前 `gcc-libs`：**16.2.1+r23**（GCC 16），`llvm-libs`：23.1.1-2
- 该 `librustc_driver` 期望 libstdc++ 导出符号 `_M_mutate` 的版本节点 `LLVM_23.1`，而 GCC 16 的 libstdc++ 里**该版本节点已不存在**（实测 `strings libstdc++.so.6 | grep -c LLVM_23` → **0**）
- → 典型的 Arch **部分升级**：`gcc-libs` 已升，`rust` 未随之重建。`cargo --version` 能跑是因为 cargo 不链接 `librustc_driver`，但**任何真正的编译都会崩**。

**处理选项（按推荐度）**

| 选项 | 命令 | 说明 |
|---|---|---|
| A（推荐） | `shelly upgrade-all`（开 `proxy_on`） | 全系统升级，最干净；顺便解决 11 天未同步的 DB |
| B | `sudo pacman -Sy --needed rust` | 只升 rust；但 `-Sy` 不 `-u` 属于部分升级，有风险 |
| C | **什么都不做** | 因为 `~/.cargo/bin` 已在 `$PATH` 最前，`rustc`/`cargo` 都解析到 rustup 版本，系统那个坏包不会被用到。**项目开发不受影响** |

> 注意：包数据库停留在 **2026-10-02**，已有 11 天。实测证据：`sudo pacman -S just` 直接失败——
> DB 里记录的是 `just-1.58.0-1`（cachyos-znver4）/`1.58.0-1.2`，而所有镜像上这些版本都已被删除（404）。
> 只要不动 pacman，这个陈旧 DB 就不会造成实际问题。

### 4.1 这条矩阵对项目的意义

**可以在 Linux 上做的事（约占工程量的 60~70%）**
- 全部 Rust 核心：数据模型、EPUB/TXT 解析、CFI 换算、分页、分词、索引、Locator 合并、HLC、冲突检测
- **为 iOS 编译校验**（`cargo check --target aarch64-apple-ios`）——能提前发现"只在 iOS 上编译失败"的问题
- **产出 iOS 静态库** `.a`（虽不能链接成 App，但可交给 Mac 直接使用）
- **生成 Swift 绑定**，并可做"绑定与 Rust 接口是否漂移"的 CI 检查
- 同步合并引擎的**收敛性随机测试**（proptest）——这是"冲突率 <1%"的核心保障
- 索引/搜索的性能基准（用真实中文语料）

**必须 macOS 才能做的事（本机没有 Mac → ⚠️ 全部只能走云端 CI）**
- 生成 `.xcodeproj`、编译 App、跑模拟器/真机
- Readium 集成与 EPUB 渲染调试
- 帧率（60fps）、内存峰值、Instruments 剖析
- PDFKit 文本提取
- 后台任务（`BGProcessingTask`）行为、热状态降级
- 崩溃率统计（MetricKit）、App Store 提审

### 4.2 本机没有 Mac —— 详见 `05-云端构建与验证方案.md`

⚠️ **已确认：开发机只有 Linux，且不打算购买 Mac。**

这意味着 Xcode / 模拟器 / Instruments / 交互式调试**全部不可用**，唯一反馈回路是云 CI（每次 10~20 分钟，异步）。
这不是"麻烦一点"，而是**项目最大的风险**，因此单独写了一份方案文档：**`05-云端构建与验证方案.md`**，其中已查证：

- GitHub Actions 的 `macos-26-arm64` 镜像自带 **Xcode 26.6**（满足 iOS 26 SDK 构建）
- **公开仓库的 macOS runner 免费且不限额度**；私有仓库约只有 **200 macOS 分钟/月**（macOS $0.062/min vs Linux $0.006/min ≈ 10 倍）
- 可以在 CI 里做：`xcodebuild build` / `test`（模拟器）/ `simctl screenshot`（截图回传）/ TestFlight 上传
- TestFlight 是**不买 Mac 也能拿到真机崩溃率与真实性能数据**的路径（需 $99/年开发者账号）

那里还有三个需要决策的问题（仓库公开/私有、是否做本地"开发壳"、是否租云端 Mac）。

## 五、`just` 任务运行器

由于 pacman 的旧 DB 指向已删除的版本（见 §三），改为**源码安装**：

```bash
cargo install just --locked        # 走 USTC crates 镜像
```

装好后把下面内容放进仓库根的 `justfile`：

```make
# ---- 通用 ----
fmt:         ; cargo fmt --all
lint:        ; cargo clippy --all-targets -- -D warnings
test:        ; cargo test --workspace

# ---- iOS 交叉（本机可跑） ----
check-ios:   ; cd core && cargo check --workspace --target aarch64-apple-ios
check-ios-sim: ; cd core && cargo check --workspace --target aarch64-apple-ios-sim
build-ios-lib: ; cd core && cargo build -p perch-ffi --release --target aarch64-apple-ios

# ---- 生成 Swift 绑定 ----
bindgen:     ; cd core && cargo run -p perch-ffi --bin uniffi-bindgen -- generate \
                 --library target/debug/libperch_ffi.so --language swift \
                 --out-dir ../ios/Generated --no-format
bindgen-drift: # CI 里跑：生成后 git diff --exit-code，防止绑定与 Rust 接口不一致

# ---- 基准 ----
bench-index: ; cargo bench -p perch-index
```
