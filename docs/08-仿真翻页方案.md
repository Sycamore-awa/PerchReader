# 仿真翻页（Google Play Books 风格）方案

> 需求来源：用户 2026-10-16 明确提出「想要那种谷歌的仿真翻页效果」。
> 这与 `项目目标.txt` 里「仿真翻页在原生自定义 View 做，Rust 算路径」一致，但**UI 栈已改为 Flutter**，
> 所以实现面从"原生自定义 View"变成"Flutter 自绘 + 平台能力"，详见下文。

## 一、目标效果

Google Play Books 的「翻页」模式：从页面边缘（通常是右下角）拖拽时，纸页像真实纸张一样被**卷起**，
露出下一页；伴随卷边阴影与被卷起纸背的高光；松手后要么回弹、要么完成翻页。
与 iBooks 的卷页类似，但 Google 的手感更"薄"、卷筒更明显。

**要素**（缺一不可）：
1. **跟手**：卷曲程度实时跟随手指，不能是固定动画
2. **卷筒**：卷起部分有圆柱感（不是单纯折叠）
3. **阴影**：卷边外有投影，卷起纸背有渐变
4. **回弹 / 完成**：松手后按速度与拖拽距离决定
5. **60fps**：这是项目目标里"基础翻页 60fps"的加分项，但也是最难达到的

## 二、⚠️ 一个必须先解决的架构冲突

**卷页动画作用在"页面位图"上，而我们的页面内容在 Readium 的 WebView / 原生视图里。**

Google 与 Apple 是这么做的：把页面**渲染成位图**，然后对位图做网格形变。我们没有现成的位图 ——
页面是 Readium 渲染器（iOS 上是 WKWebView 系的导航器，Android 上是 Readium Kotlin 的
WebView 复用列表）里的活视图。

`flutter_readium` **没有暴露任何"页面截图"能力**。所以要做卷页，必须先拿到页面位图，有三条路：

| 方案 | 做法 | 代价 | 风险 |
|---|---|---|---|
| **A. 平台通道截图** | iOS 用 `drawHierarchy`/`snapshotView`，Android 用 `View.draw(Canvas)`，把 Readium 的视图截成位图 | 要写 iOS/Android 平台代码 | **必须有 Mac / 真机才能调试**；且要拿到 Readium 内部视图的引用（可能需要 fork flutter_readium） |
| **B. 用 Flutter 自绘页面** | 不用 Readium 的分页渲染，改为：Rust 算分页 → Flutter 原生绘制文字 → `RepaintBoundary.toImage()` 拿位图（Flutter 内很容易） | 放弃 Readium 的复杂 EPUB 排版能力（CSS、图文混排） | 两种渲染器并存，风格不一致；只适合 TXT 或简单 EPUB |
| **C. fork flutter_readium** | 在插件内部暴露导航器的页面视图/位图 | 维护成本；上游升级要重新合 | 上游是活跃小型项目，fork 后合并压力大 |

**我的判断**：**A 是唯一能"保留 Readium 渲染质量"的路**，但它需要平台代码 + 真机调试，
在没有 Mac 的条件下**无法验证**。因此这件事的可行性研究应当**尽早做一个小实验**，
而不是等到 M6 才发现做不了（详见 §五）。

## 四、Rust 该做什么（对应项目目标里的"Rust 算路径"）

卷页的**几何与着色参数是纯计算**，正好适合放进 Rust 核心，而且**能在 Linux 上完整测试**：

```
输入：拖拽点 (x, y)、页面尺寸、卷曲半径上限、当前拖拽阶段
输出：贝塞尔控制点序列（卷边曲线、卷筒背面曲线）、阴影渐变参数、位图网格的形变控制点
```

好处：
- 手感调参变成"改一组纯函数参数 + 跑单测/黄金测试"，不依赖设备
- iOS / Android / 未来 Web 共用同一套卷页几何，效果一致
- 可以在 Linux 上用**黄金测试**（给定输入 → 断言输出坐标序列）锁定行为，防止调参调坏

Dart 侧只负责：把 Rust 给的几何数据画出来 + 处理手势与动画驱动。

## 五、建议的排期（重要）

| 阶段 | 做什么 | 前置条件 |
|---|---|---|
| **现在（可做）** | ① Rust 卷页几何模块 + 黄金测试；② 调研确认 A 方案的截图可行性 | 无（纯本机） |
| 有设备后 | ③ 平台通道截图打通；④ 接 `page_curl_flip` 的 CurlOverlay；⑤ 手感调参 + 60fps 优化 | **必须有 Mac / 真机** |
| M6 | 与滚动模式并存、可切换；无障碍与低性能设备降级（直接关掉动画） | 同上 |

**必须在"没有 Mac"阶段就做掉的事**：确认 **A 方案（平台截图）到底可不可行**。
这是整个效果的前提；如果 Readium 的视图拿不到或截不到，就得回到 B（自绘）或 C（fork）。
**这个结论越早拿到越好**，因为它可能反过来影响 UI 技术栈的选择。

**降级策略**：卷页是最容易在低端设备上掉帧的功能，因此**必须**保留"无动画翻页 / 滚动模式"作为默认或兜底，
并把卷页做成设置项（默认开或关，待真机数据决定）。

## 十、几何模型已实现并验证（2026-10-16）

`core/perch-pagecurl`（15 个测试，零依赖）。采用的模型：

1. **折线** = 被拖动角与手指位置的**垂直平分线**
2. **圆柱中心在纸面正上方**（`M + r·ẑ`）——因为纸是平着进入折线的，
   切线必须落在纸面内，否则折线处会出现折痕感
3. **卷角** `φ = h/r`（h 为角到折线的纸长），上限 π
4. **投影带宽** `r·sin(min(φ, π/2))`：φ>π/2 后纸绕到圆柱背面被自身遮挡，
   边界变成圆柱轮廓 r

测试逼出的两个真错误（都不是笔误）：

- **半平面方向搞反了**：被卷起的是"靠近被抓的角"那一半，剩下不动的是手指那一侧。
  按原来的写法，拖得越远剩下的正面反而越大
- **圆柱位置错**：原本沿纸面偏移 `M + r·u`，不满足切线连续；带宽公式也因此错成
  `r(1-cosφ)`。顺带发现按原公式 `paper_edge_extent` 恒等于 `band_extent`（冗余字段，已删）

**已知近似**：固定半径下，"角点落在手指处"只在 `r·sin(h/r) = h` 时精确成立。
真机调参时可让 r 随 h 变化，或靠手势在完成前结束来掩盖差异。

**仍未做**：平台截图可行性（§二 方案 A）、Dart 绘制层、真机手感调优。
