# PerchReader iOS 阶段 — 里程碑拆解

> ⚠️ **2026-10-16 变更**：UI 技术栈已定为 **Flutter**（见 `06-UI技术栈决策.md`）。
> 本文中 M2 提到的 Swift/Readium Swift/PDFKit/WKWebView 应替换为：
> **Flutter + `flutter_readium`（EPUB 渲染，底层官方 Readium Swift/Kotlin/JS）**。
> PDF 的**结构**（页数/大纲/元数据）由 `core/perch-pdf` 在 Rust 侧解析，**正文抽取仍是平台 port**；
> 渲染层目前**没有**引入 `pdfrx`（`app/pubspec.yaml` 里没有该依赖，2026-10-17 核对）。
> 里程碑划分、验收标准、验证位置分层**均不变**。
> 另：由于**没有 Mac**，"验证位置 = Mac" 的项目一律改为**云端 macOS CI**（见 `05-云端构建与验证方案.md`）。

> 范围声明：本阶段**只做 iOS**。Android / Web / 桌面 不在交付范围内，但架构上预留（Rust 核心 + 手写 C ABI/JSON 契约不写死 iOS 假设）。
> 曾计划用 UniFFI 做绑定层，**已改为手写 C ABI + JSON 契约**（原因见 `10-进度与交接.md` §三）。
> 目标来源：`项目目标.txt` 的四个量化目标（导入快 / 阅读稳 / 同步准 / 架构可扩展）。

| 里程碑 | 主题 | 对应目标 | 依赖 | 主要验证位置 |

## M0 — 地基与可验证闭环

**目标**：让「写完就能验」这条链路存在。**本机没有 Mac，所以「云端 macOS 编译 + 模拟器测试 + 截图」必须在这一步就建好**，否则后面所有 Swift 代码都是盲写。

**交付物**
- 仓库骨架：Rust workspace（`core/`）+ Flutter 工程（`app/`，含 `app/ios/`）+ `docs/` + `justfile`
- Rust 核心最小可编译单元，且**能为 iOS target 编译**（`cargo check --target aarch64-apple-ios`）
- FFI 契约打通：`core/perch-ffi` 手写 C ABI（`perch_call` / `perch_string_free`）+ JSON 契约
  —— 曾计划用 UniFFI 生成 `.swift`/`.h`/`.modulemap`，**已放弃**：生成物在 Linux 上无法链接验证，改为可在 Linux 用 `dart:ffi` 端到端验证的手写 ABI（见 `docs/10` §三）
- iOS 工程以 **`flutter create` 生成的 `app/ios/Runner.xcodeproj`** 描述并提交进仓库
  —— 曾计划用 `project.yml`（XcodeGen）+ CI 生成工程，**未采用**
- **CI 三 job 流水线**（详见 `05-云端构建与验证方案.md` 与 `.github/workflows/ci.yml`）：
  - `core-linux`（ubuntu）：fmt / clippy / test / `check --target aarch64-apple-ios` / iOS 符号导出断言
  - `ffi-smoke`（ubuntu）：编 `.so` 并用 `dart:ffi` 端到端调用（55 项）
  - `ios-macos`（`macos-26`）：`flutter build ios --simulator` + **断言 Rust 符号确实链进 app bundle**
- 文档：`docs/01`~`docs/11`（含技术考证、spike 报告、翻页方案、UI 设计方案、进度交接）

**验收标准**
- `just check-ios` 通过（Linux 本地）
- `just ios-symbols` 通过：iOS 静态库里 `_perch_call` / `_perch_string_free` 是全局导出符号（`T`）
- `just test` 通过（Linux，宿主）
- **CI 绿**：Rust 核心全测试通过 + iOS App 在 macOS runner 上**编译通过**（含符号断言）
- iOS 符号断言在 Linux 上可跑，在 CI 上强制开启（`PERCH_REQUIRE_LLVM_NM=1`，缺 `llvm-nm` 直接失败而不静默跳过）

**验证位置**：前三条 Linux 本地 ✅；后两条需云端 CI（在 `macos-26` 上跑，2026-10-17 已全绿）

> ✅ 仓库可见性**已定：公开**（2026-10-16），见 `05` 文档 §六。

## M1 — 书库与导入登记（三阶段管线的第一阶段）

**目标**：**感知上架**。1000 本书在 10 秒内全部出现在书架上。

**核心设计**：导入拆三阶段，M1 只做第一阶段。

| 阶段 | 做什么 | 耗时预算 | 何时执行 |
|---|---|---|---|
| ① 登记 | 复制/硬链文件进沙盒 + 算指纹 + 插一行 `state=registered` | 单本 ~ms | 前台，用户点导入后立即 |
| ② 精修 | 解析元数据 / 封面 / 目录 / 字数 | 单本 50~300ms | 后台，低优先级 |
| ③ 索引 | 全文倒排索引 | 单本 0.5~5s | 后台，可延迟/可暂停 |

关键点：**① 阶段不打开文件内容**。这一点是"1000 本 <10s"能成立的根本原因，也是后续所有性能回归的红线。

**交付物**
- 数据模型（Rust `perch-model`）：`Book` / `BookId` / `Locator` / `Annotation` / `ImportState` / `Format`，
  用 `serde` 序列化后**以 JSON 跨 FFI 传递**
  —— 原文写的是"全部 `uniffi::Record`"且多列了一个 `BookSource`；两者都与实现不符（无 UniFFI，无 `BookSource` 类型，2026-10-17 核对）
- 进度存储：Dart 侧接口 `ProgressStore` + 当前实现 `JsonFileProgressStore`（每本一个 JSON 文件）
  —— 原文写"SQLite schema + 迁移机制（iOS 侧实现，GRDB）"，**尚未落地**；`ProgressStore` 接口保证将来换 SQLite 时上层不动
- 指纹与去重：`(size, 首尾 64KB 哈希, 首块内容哈希)`，重复导入不产生副本（`perch-import`）
- 批量导入入口：`UIDocumentPicker` / 文件 App / 分享扩展
- 书库 UI：网格 + 列表、排序（最近/标题/作者）、筛选（格式/阅读状态）、封面占位
- 导入任务的状态可视（"正在精修 N 本"）

**验收标准**
- 1000 本登记（① 阶段）**< 10s**，且首架渲染完成后无卡顿
- 导入过程中杀进程 → 重启后任务自恢复，不产生重复条目
- 同一文件导入两次 → 只有一条记录
- 书库滚动 60fps（1000 项，用 `UICollectionViewDiffableDataSource` + 预取）

**验证位置**：指纹/去重/状态机/基准测试 **Linux 可验**（用 1000 个合成文件跑 `just bench-register`，实测 1000 本 56 ms）；书库 UI 必须 Mac。

**风险**
- "感知上架"定义需澄清：是"1000 条记录进 DB"还是"1000 个封面渲染出来"？建议定义为**用户看到 1000 本书的列表可交互**（封面可用占位）。
- 沙盒复制 1000 个文件本身可能是瓶颈（尤其从 iCloud Drive）→ 用 `NSFileCoordinator` + 并行复制 + 进度反馈。

## M2 — 阅读器 MVP（EPUB / TXT / PDF）

**目标**：打开 <1s，基础翻页 60fps。

**交付物**

| 格式 | 渲染方案 | 进度定位 |
|---|---|---|
| EPUB | Flutter `flutter_readium`（底层官方 Readium Swift/Kotlin/JS，锁 3.11.0） | Readium `Locator`（`partialCfi` 口径见 `docs/02` §七点五） |
| PDF | 结构（页数 / 大纲 / 元数据）由 Rust `perch-pdf` 解析；**渲染层未接入**（`pdfrx` 未引入） | 页码 + 归一化坐标 |
| TXT | Rust `perch-txt` 探测编码（`chardetng`）+ 解码（`encoding_rs`）+ 字符/行索引；渲染层未接入 | 字符绝对偏移 |

> 上表原文是 Swift 方案（Readium Swift `EPUBNavigatorViewController` / PDFKit `PDFView` / `UITextView`）。
> UI 栈改为 Flutter 后，**EPUB 渲染改走 `flutter_readium`**；PDF/TXT 的渲染层目前还没有代码，
> Rust 侧只提供结构解析与定位换算（2026-10-17 核对 `app/pubspec.yaml` 与 `app/lib/main.dart`）。

**必须做的设计**
- **统一 Locator**（Rust 定义）：三种格式映射到同一结构，且 **JSON 结构与 Readium 的 Locator 对齐**，使 Readium ↔ 我们 的互转近乎零成本
- 进度持久化：切后台 / 退出 / 每翻 5 页写一次；冷启动恢复到上次位置
- 阅读设置：字号、行距、主题（白/棕/黑）、翻页方式（滚动/翻页）、边距
- 三方格式的**首屏路径**不做重活（不生成封面、不建索引）

**验收标准**
- 三种格式打开到首屏 <1s（p90）：20MB EPUB / 300 页图文 PDF / 10MB TXT
- 滚动/翻页 60fps（`CADisplayLink` 或 Instruments 测），无 >100ms 的卡顿
- 冷启动恢复定位偏差：EPUB ±1 屏内，PDF 精确到页，TXT 精确到段
- 崩溃率基线建立（MetricKit 接上）

**验证位置**：Locator 换算、TXT 分页算法、CFI 生成 **Linux 可验**（纯逻辑 + 语料单测）；渲染与帧率必须 Mac + Instruments。

**风险**
- Readium **4.0.0-alpha.2** 已存在，但**不要碰**（alpha 不能作为交付基础）。锁 3.11.0。
- 仿真翻页（page-curl）**不在 M2**，放到 M6。M2 只做滚动/无动画翻页。
- WKWebView 内存：EPUB 大图多时容易爆，需要资源分片加载与 WebView 复用策略。

## M3 — 后台精修 + 延迟索引 + 搜索

**目标**：把"上架快"和"可用"解耦 —— 书先上架，内容后台补齐。

**交付物**
- ② 精修：EPUB 的 OPF 元数据 / 封面 / NAV 目录 / 字数；PDF 的页数 / 大纲 / 元数据；TXT 的编码 / 字数 / 首行标题猜测
  （PDF **不渲染、不抽正文**，因此"首屏缩略图"不属于 Rust 侧）
- ③ 索引：全文倒排索引，中文用 **CJK bigram 切分**（免词典），英文用 unicode 词边界
  —— 原文写了 "`fst` 支持前缀补全"，**未实现**：`core/perch-index` 明确标注「未实现前缀/模糊匹配」（2026-10-17 核对）
- 调度器：`BGProcessingTask` + 低优先级队列；热状态（`ProcessInfo.thermalState`）降级；低电量/蜂窝网络暂停；可暂停/恢复
  （纯逻辑已在 `perch-pipeline` + `perch-jobs::Pipeline`，**平台侧后台队列尚未接**）
- 搜索 UI：输入即搜、结果按章节分组、点击跳转并高亮（用 Locator）

**验收标准**
- 导入 1000 本后，后台精修 + 索引在设备空闲时完成，且**前台帧率不受影响**（前台卡顿无 >50ms 的帧）
- 20 万字 TXT 建索引 <5s；1000 本全部索引后的索引体积 < 原书体积 40%
- 搜索首字响应 <200ms（10 万词条规模）
- 搜索跳转定位准确率 100%（用 Locator 回放测试）

**验证位置**：索引构建、分词、搜索排序 **Linux 可验**（用真实中文/英文语料跑基准，结果写进 `docs/` 作为回归基线）；后台调度行为需 Mac。

**风险**
- 后台任务被系统杀死 → 必须做到**每本书的索引是独立可重入的**，杀在哪都不留半成品
- 索引体积膨胀 → 落盘用**分片 + delta+varint 编码**（`core/perch-index/src/persist.rs`）
  —— 原文写"压缩（`zstd`）"，实际**未引入 `zstd`**，紧凑性靠 delta+varint 拿到

## M4 — 标注（高亮 / 笔记 / 书签）

**目标**：能标、能看见、**重排后不漂移**。

**交付物**
- 文本选择 → 生成**范围 Locator**（起点 + 终点）
- 高亮 / 下划线 / 波浪线 / 颜色；笔记（附加文本）；书签
- **锚点重定位**：字号/行距/主题/分栏变化后，用 `Locator 范围 + 前后文 excerpt` 做二次定位
- 标注列表（按书 / 按时间）、跳转、编辑、删除
- 导出：Markdown / JSON（含原文摘录）

**验收标准**
- 字号从最小到最大、主题切换、横竖屏切换后，标注**零漂移**（自动化重放测试，成功率 >99%）
- 1 万条标注时列表滚动流畅
- 跨版本（同一本书换 EPUB 文件 但内容相同）标注仍能定位（容错匹配兜底）

**验证位置**：范围 Locator 生成、重定位算法、容错匹配 **Linux 可验**（纯逻辑，可用构造语料 + proptest）；选择手势与原生渲染必须 Mac。

**风险**
- EPUB 重排后文本节点变化是行业难题。策略：**首选 CFI 精确定位，失败则 excerpt 模糊匹配**，两者都失败则降级为"章节 + 大致进度"并提示用户。

## M5 — 同步（进度 / 书签 / 笔记）

**目标**：冲突率 <1%。

**交付物**
- 传输层：**CloudKit 私有数据库**（不自建服务器、不自建账号，身份用 Apple ID）
  —— 原文写"自建最小 API（Rust `axum`）或 Supabase + Sign in with Apple"，**已作废**（2026-10-17 决策，见 `docs/04` #8）
- 客户端：`CKServerChangeToken` 增量拉取、断网重试；书文件走 `CKAsset`
  （`perch-sync::SyncServer` 降级为**测试替身**，`wire` 的 JSON 形状继续用）
- **合并引擎（Rust）**：混合逻辑时钟（HLC）+ 每字段 LWW + 墓碑删除；标注按 UUID 逐条独立，减少冲突面
- 冲突埋点：每次合并记录（保留/丢弃/合并），本地可查 + 可选上报
- 冲突率统计面板（开发用）

**验收标准**
- 构造并发场景（两设备同时改同一本书的进度/同一条标注）→ **冲突率 <1%**，且无数据丢失
- 离线编辑 100 条 → 联网后自动收敛，最终两设备状态一致（同样输入 → 同样输出，幂等）
- 同一 Locator 重复上行幂等；**跨设备主键用 `fingerprint` 而不是 `BookId`**（后者是本机随机 UUID）
- 同步不影响前台：后台 + 低优先级，单次同步流量可观测

**验证位置**：**合并引擎与收敛性 100% Linux 可验** —— 用 `proptest` 生成随机并发操作序列，断言"任意顺序应用后状态一致"（这才是"冲突率 <1%"的真正护城河）；网络与后台行为需 Mac；CloudKit 接入本身**只能在真机/模拟器上验**（无 Mac → 未开始）。

**风险**
- 冲突率 <1% 需要先**定义**指标：建议 = 被丢弃的字段级变更数 / 总字段级变更数。定义不同，数字差十倍。
- 进度语义冲突："最后读到的位置" vs "最远读到的位置" —— 需要产品决策（见待决问题）。

## M6 — 打磨与上线准备

**交付物**
- **仿真翻页**：**Flutter 自绘**做卷页动画，**Rust 算路径**（折线/圆柱中心/卷角/投影带宽，见 `core/perch-pagecurl`），与滚动模式并存可切换
  —— 原文写"iOS 原生自定义 View"；UI 栈改为 Flutter 后，绘制层是 Flutter 自绘，
  **不用 `page_curl_flip`**（几何写死全宽剥页、无手指坐标，`docs/09` §A.5）
- 崩溃与性能：MetricKit（免第三方、隐私友好）+ 自建符号化上报；`os_signpost` 关键路径埋点
- iPad 适配：分栏、Slide Over、分屏、横屏
- 无障碍：Dynamic Type、VoiceOver、对比度；深色模式
- 本地化（中文优先，预留英文）
- 隐私：`PrivacyInfo.xcprivacy`、App Store 提审材料
- **DRM / 支付：只留接口，不实现**（按项目目标，属于"后续"）

**验收标准**
- 崩溃率 <0.1%（MetricKit 统计口径，需要足够样本量）
- 冷启动 <1.5s；内存峰值 <300MB（1000 本书库 + 打开一本书）
- 仿真翻页稳定 60fps（这是最难的性能项，放最后做）

**验证位置**：Rust 路径计算 Linux 可验（给定参数输出坐标序列的黄金测试）；其余需 Mac + 真机。

## 二、关键风险与红线

| 风险 | 影响 | 对策 |
|---|---|---|
| 无 Mac 时无法真机验证 | 渲染/帧率/手势全部堆积到后期 | 按"验证位置"分层：把尽可能多的逻辑搬到 Linux 可验层（本拆解已如此设计） |
| Readium 4.0 alpha 诱惑 | 稳定性风险 | 锁 3.11.0，升级单独排期 |
| "1000 本 <10s" 定义模糊 | 验收扯皮 | 先定义再实现（见待决问题 #15） |
| 崩溃率 <0.1% 需样本量 | 早期无法度量 | M2 起就接 MetricKit，先建立基线 |
| 仿真翻页人力大 | 拖慢主线 | 明确放 M6；M2 交付滚动即可用 |
| 系统 rustc 损坏（本机） | 干扰开发 | 已用 rustup 隔离，见 `03-环境与验证矩阵.md` |

## 三、不在本阶段范围

Android、Web、桌面壳（Tauri）、DRM 实现、支付实现、云同步服务端之外的运维（监控/告警/扩容）。
但：**Rust 核心的 API 设计不得违反跨端原则**（不返回 iOS 专属类型、不假设 Foundation 存在、不泄漏 `objc`/`wkwebview` 概念）。
