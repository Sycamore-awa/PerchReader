## 二、问题 A：卷页位图

### A.1 三条前提修正（先纠偏，再谈方案）

**修正 1：拿 WKWebView 不需要 fork。**

`flutter_readium` 的 iOS 侧 `EPUBReaderView` 确实有 `let readiumViewController: EPUBNavigatorViewController`（internal，非 private），
但真正持有 WebView 的类是 internal 的：

```swift
// readium/swift-toolkit @3.11.0  Sources/Navigator/EPUB/EPUBSpreadView.swift
class EPUBSpreadView: UIView, Loggable, PageView {   // internal，非 public
    let webView: WebView                            // internal
}
// Sources/Navigator/Toolkit/WebView.swift
final class WebView: WKWebView { ... }               // internal
```

**关键**：`WebView` 继承自 `WKWebView`，而 `WKWebView` 是公开的 Apple 类。
所以从 `readiumViewController.view` 递归 `subviews`、`guard let wv = v as? WKWebView` 即可拿到，
**不需要 fork swift-toolkit，也不需要反射**。

**修正 2：只需要 1 张位图，不是"当前页 + 下一页"两张。**

行业做法（见 A.4）是：**截"正在离开的那一页" → 盖 overlay → 底下瞬时跳页 → 动画 → 拆 overlay**。
下一页本来就是 live 的、已经在底下，卷起时自然会露出来。这一条把整个方案的成本砍掉一半。

**修正 3：`flutter_readium` 的 Dart API 里没有任何截图入口——这点核实无误。**

对全仓 `*.swift` + `*.dart` grep `snapshot|screenshot|drawHierarchy|toImage|RepaintBoundary`：
除了 Readium 自己内部翻页用的 `snapshotView` 与 Flutter 示例里的 `AsyncSnapshot`，**零命中**。
所以原生侧代码必须我们自己加。

### A.2 位图从哪来：`takeSnapshot`，不要 `drawHierarchy`

**决定性证据来自生产实现**，不是推测。

iOS（`readest/readest` @main，`plugins/tauri-plugin-native-bridge/ios/Sources/NativeBridgePlugin.swift:2130`）：

```swift
let config = WKSnapshotConfiguration()
config.rect = CGRect(x: args.x, y: args.y, width: args.width, height: args.height)
// snapshotWidth 是 points；生成的是 snapshotWidth × screen-scale 像素宽，
// 所以 width × (2/scale) points 在 3x 屏上得到 2x CSS 像素的位图
let scale = webView.window?.screen.scale ?? UIScreen.main.scale
if scale > 2 {
  config.snapshotWidth = NSNumber(value: args.width * 2.0 / scale)
}
webView.takeSnapshot(with: config) { image, error in
  DispatchQueue.global(qos: .userInteractive).async {
    guard let data = image.jpegData(compressionQuality: 0.9) else { ... }
    invoke.resolve(["data": data.base64EncodedString()])
  }
}
```

Android 侧注释把"为什么不用 `View.draw`"写得很直白：

> "PixelCopy reads back from the window surface, which includes the hardware-accelerated WebView
> that **View.draw would miss**."

**`drawHierarchy` 对离屏内容有效吗？——不可靠，别依赖它。**

| 事实 | 出处 |
|---|---|
| Apple 定义 `drawHierarchy(in:afterScreenUpdates:)` 为 "Renders a snapshot of **the complete view hierarchy as visible onscreen**" | Apple 官方文档 |
| 它是 UIKit 层绘制路径，而 WKWebView 的内容在**独立进程**渲染 → video / WebGL / canvas 得到黑块 | StackOverflow #60320870 / #45690932 / #68219228 |
| Readium 自己翻页用的 `snapshotView(afterScreenUpdates:false)` 返回的是 **UIView 不是位图**，且对未渲染视图会拿到空白 | `PaginationView.swift:351`；SO #27410991「the snapshot is a blank UIImage because the snapshotView isn't rendered」 |
| `takeSnapshot` 是 Apple **专门为此提供**的 API："Generates a platform-native image from the web view's contents asynchronously"，走 WebContent 进程渲染，**不依赖视图可见性** | Apple 官方文档 |

**那"下一页"真要截的时候怎么办？**（两栏 spread 要看背面时）

Readest 的做法是拿一个快照视图当"盾牌"盖住屏幕，在它底下偷偷渲染，再截图
（`NativeBridgePlugin.swift:2173` `cover_webview_region`）：

> "Freeze the on-screen pixels of a region of the webview behind a snapshot of what is currently
> presented there... The snapshot view is a sibling above the webview: **`takeSnapshot` renders the
> webview's own layer tree**, so the JS side can expose the incoming column underneath, capture it
> with `capture_webview_region`, and restore its overlay — all while the user still sees the frozen
> old pixels."

即：**盖盾 → 底下换页 → 截图 → 还原 → 撤盾**。这是"离屏内容"唯一干净的解法。

### A.3 预渲染策略：两层，别混为一谈

**第一层：DOM 预载——Readium 已经做了，且已暴露给我们。**

```dart
// flutter_readium/lib/reader_widget.dart
this.preloadPreviousPositionCount = 2,
this.preloadNextPositionCount = 6,   // 默认预载后面 6 个 position
```

源码层面，每个预载 position 是一个**独立的 `EPUBSpreadView` + 独立 `WKWebView`**，
并且已经 `scrollView.addSubview(view)` 排好版（`PaginationView.swift:259`）。
所以"翻页瞬间下一页还没渲染完"在 Readium 里**基本不成立**。

> 注意：`preloadNextPositionCount` **只有 iOS 生效**，kotlin-toolkit 没在公开配置里暴露（README 明确写了）。

**第二层：位图预热——这一层 Readium 不管，必须我们自己做。**

Readest 的实测数据（`.claude/memory/page-turn-styles-viewtransitions-555.md` 原文）：

> "**Android perf gotcha (user-verified fixed)**: full-density PNG encode = **~1.5s/turn** on Xiaomi 13
> (3x, 1080×2400) → **curl read as broken**; fix = **JPEG q85 (q90 since PR #5208) + dest bitmap
> capped at 2× CSS px** (PixelCopy scales into a smaller dest for free) → invoke **1550ms→34ms**,
> overlay mounts 132ms after tap; JS must NOT hardcode blob type 'image/png' (decoder sniffs).
> iOS same optimization: `jpegData(0.85)` off-main + `WKSnapshotConfiguration.snapshotWidth = width*2/scale`
> when scale>2 (snapshotWidth is in POINTS; image px = points×scale)"

预热时机：

```js
const PREPARED_CAPTURE_DELAY_MS = 160;         // 页面稳定后 160ms 空闲预热
const PREPARED_CAPTURE_CHROME_DELAY_MS = 360;  // 有 chrome 时 360ms
```

监听 `relocate` / `draw-annotation` / `stabilized` 等事件 → invalidate + 重新预热，翻页时直接用暖图。

**"翻页时先截一张空白的"——方向反了。** Readest 是**先铺同色平面**：

> "At progress = 0 the flat strips tile the full page width and hide this layer completely,
> making the capture transition invisible."

即用与纸张同色的平面顶上，**截图失败就退化成纯色纸**，而不是白屏。

**一个独立收敛的数字**——`page_curl_flip` 0.2.4 的 `lib/src/capture.dart`：

```dart
/// The pixel ratio to capture at for [context]: the device's own ratio,
/// **capped at 2.0** — a page in mid-curl cannot show 3× detail, and the
/// uncapped bitmap on a flagship costs ~12–16 MB per flip.
double captureRatioOf(BuildContext context) =>
    math.min(View.maybeOf(context)?.devicePixelRatio ?? 1.0, 2.0);
```

**两个互不相关的项目都撞到 2× 这个上限**——直接采纳。

### A.4 开源先例：确实有人做过，而且不止一个

#### ① Readest（25,328 ★，Tauri + foliate-js）——最完整的参考

完整管线 `capture → overlay → instant-nav → animate`：

| 文件 | 作用 |
|---|---|
| `src/app/reader/utils/capturedTurn.ts` | 编排层（50 KB，host-callback 注入，可单测） |
| `src/utils/pageCurl.ts` | **WebGL mesh curl 渲染器** |
| `src/app/reader/hooks/useCapturedTurn.ts` | 手势拦截 + 空闲预热调度 |
| `plugins/tauri-plugin-native-bridge/ios/Sources/NativeBridgePlugin.swift` | iOS 截图（`takeSnapshot`） |
| `plugins/tauri-plugin-native-bridge/android/.../NativeBridgePlugin.kt` | Android 截图（`PixelCopy`） |

`pageCurl.ts` 的文件头几乎是照着我们的问题写的：

> "Draws a **captured page bitmap** as a grid mesh deformed around a cylinder — the classic page curl...
> The renderer **knows nothing about capture or gestures**: callers provide an `ImageBitmap` of the
> outgoing page and drive `render(progress, grab)`."

它 shader 的 uniform 是 `uFold`（折痕上一点）、`uDir`（折痕法线）、`uRadius`（圆柱半径）、`uLeaf`（可形变区间）——
**和我们 `core/perch-pagecurl` 是同一个几何模型**。分层方式也和我们一样（渲染器不管捕获）。

**值得对表的两处**：

```glsl
if (s < PI * r) {                    // φ < π
  float wrapped = r * sin(s / r);
  float z = r * (1.0 - cos(s / r));
  p -= uDir * (s - wrapped);
  lift = z / (2.0 * r);
} else {                             // 过了半圈：平铺在顶上，关于折痕镜像
  p -= uDir * (2.0 * s - PI * r);
  lift = 1.0;
}
```

我们 `core/perch-pagecurl/src/lib.rs:251-254` 是：

```rust
let curl_angle = (half / radius).min(PI);
let visible_angle = curl_angle.min(PI / 2.0);
let band_extent = radius * visible_angle.sin();     // = r·sin(min(φ, π/2))
```

两套都在 `r·sin(φ)` / `r·(1-cos φ)` 这个家族里，但**边界处理不同**：
我们在 `φ = π/2` 截断（`band_extent` 此后恒为 `r`），Readest 一路算到 `φ = π` 再切"平铺镜像"分支。
两者算的量不完全等价（我们是**带宽上界**，它是**逐顶点位移**），但 **`φ > π/2` 之后的行为值得专门做一组黄金测试交叉验证**。

另外它记了两条我们迟早会踩的：
- `travel = w + PI*r_end`（折痕线的总行程）
- `corner-grab fold tilt must decay (1-p)`（角拖拽时折痕倾角随进度衰减）

### A.5 ⚠️ `page_curl_flip` 的真实契约（修正 `docs/08` 的判断）

`08` 把 `page_curl_flip` 列为首选，理由是"CurlOverlay 设计正好匹配我们的处境 —— 你自己驱动"。
下载 0.2.4 源码核对后，**这个判断需要修正**。

`lib/src/curl_overlay.dart` 的**全部**公开入参：

```dart
const CurlOverlay({
  super.key,
  required this.progress,      // 只有一个 0~1 的进度值
  this.pageImage,              // ui.Image?  ✅ 可以喂外部位图（"Takes priority over child auto-capture"）
  this.pageColor = Colors.white,
  this.backgroundImage,
  this.child,
  this.padding = EdgeInsets.zero,
  this.shine,
  this.shadow,
});
```

类文档第一句：

> "Tiles the screen with vertical polygon slices transformed by a cylindrical projection so the
> ensemble looks like a physical page **peeling away from left to right**."

**问题**：
1. 它是**全宽左右剥页**（`progress` 0=平铺 / 0.5=最紧圆柱 / 1=完全揭开），
2. **没有任何手指坐标入参，也没有几何注入点**，
3. 我们 Rust 里那套"被拖动角与手指的垂直平分线 + 圆柱中心在纸面上方 + 投影带宽"是**角拖拽模型**，接不进去。

**→ "用 `page_curl_flip`" 和 "用我们的 Rust 几何" 是互斥的二选一，必须现在决定。**

它仍然有价值：`CurlOverlay(pageImage:)` 确实接受外部位图、MIT 许可、零依赖、`toImageSync` 保持 GPU 驻留，
可以当**兜底实现**或**参考实现**（它的 `capturePage` / 2× 上限 / 同色平面兜底三招都值得抄）。

其他元数据：MIT License，零依赖，`sdk: ^3.6.0` / `flutter: >=3.27.0`，声明支持 android + ios。

### A.6 问题 A 的建议

1. **先做二选一决策**：卷页绘制层是自绘（保住 Rust 角拖拽几何）还是用 `page_curl_flip`（放弃角拖拽）。
   建议**自绘**——`08` §四"Rust 算路径"是项目目标里写着的，而且 15 个测试已经做完了几何。
2. **只截 1 张**"离开的那一页"。
3. iOS 用 `WKWebView.takeSnapshot` + `snapshotWidth = width*2/scale`（scale>2 时）+ `jpegData(0.9)`；
   Android 用 `PixelCopy`（不是 `View.draw`）。
4. **空闲预热**（页面稳定后 ~160ms），不要等手势开始才截。
5. 拿不到图时**退化为同色平面**，不要白屏。
6. 把 `docs/08` §二方案表里的"可能需要 fork flutter_readium"改成"**不需要 fork，遍历视图树即可**"。

## 三、问题 B：标注重定位

已通读 `hypothesis/client@main` 的 `src/annotator/anchoring/` 全部相关源码。

### B.1 归一化规则：几乎不归一化（反直觉但是事实）

| 我们问的 | Hypothesis 实际做法 | 出处 |
|---|---|---|
| Unicode 归一化 | **NFKD**，但**只在 PDF 路径**用（`translateOffsets(..., {normalize:true})`）；**HTML/EPUB 路径完全不用** | `src/annotator/util/normalize.ts` |
| 空白折叠 | **不做**。用原始 `textContent` | `text-range.ts` / `types.ts` |
| 换行 | **只把 `<br>` 替换成一个空格**，仅此而已 | `rendered-text.ts` |
| 大小写 | 不处理 | — |
| 标点 | 不处理 | — |

`rendered-text.ts` 原文：

> "Store the quote with each `<br>` substituted by a space, so that selections spanning a line break
> aren't run-together as 'foobar' for `<p>foo<br>bar</p>`. Prefix and suffix go through the same
> substitution so the three fields are consistent."

**→ 结论：我们 `anchor.rs` 的"空白容忍回退"是超出 Hypothesis 的，不是落后于它。这是我们的优势，保留。**

### B.2 模糊度度量：编辑距离，不是最长公共子串

`match-quote.ts`：

```ts
const maxErrors = Math.min(256, quote.length / 2);   // 允许 一半 的字符出错！
const matches = search(text, quote, maxErrors);
```

而且有个**先精确后模糊**的快路径，很容易被忽略：

```ts
// 先穷举精确匹配；只要有一处精确命中，就不做近似搜索
while (matchPos !== -1) {
  matchPos = text.indexOf(str, matchPos);
  if (matchPos !== -1) { exactMatches.push({...}); matchPos += 1; }
}
if (exactMatches.length > 0) { return exactMatches; }

// 没有任何精确命中，才做昂贵的近似搜索
return approxSearch(text, str, maxErrors);
```

用 `approx-string-match` 这个独立的 npm 包（不是自研）。复杂度 `O((maxErrors / 32) * text.length)`。

### B.3 多次出现 & position hint：答案是 YES

**打分公式（权重硬编码）**：

```ts
const quoteWeight  = 50;   // 1 - match.errors / quote.length
const prefixWeight = 20;   // 前文相似度
const suffixWeight = 20;   // 后文相似度
const posWeight    = 2;    // 位置先验，仅作 tie-breaker

const rawScore = 50*quoteScore + 20*prefixScore + 20*suffixScore + 2*posScore;
const normalizedScore = rawScore / (50 + 20 + 20 + 2);   // 92
```

**position hint 确实存在**，来源在 `html.ts` 的 `anchor()`：

```ts
case 'TextPositionSelector':
  position = selector;
  options.hint = position.start;   // ← TextQuoteSelector 的 hint 就来自这里
  break;
```

```ts
let posScore = 1.0;
if (typeof context.hint === 'number') {
  const offset = Math.abs(match.start - context.hint);
  posScore = 1.0 - offset / text.length;
}
```

权重只有 **2/92 ≈ 2.2%**——很弱，但足以在"同一句话在正文里出现两次"时打破平局。
**这正是我们缺的那一块：我们已经有 CFI 和 progression，完全可以拿它当 hint。**

**上下文长度：`contextLen = 32`**，硬编码（`TextQuoteAnchor.fromRange`）：

```ts
// Number of characters around the quote to capture as context. We currently
// always use a fixed amount, but it would be better if this code was aware
// of logical boundaries in the document (paragraph, article etc.) to avoid
// capturing text unrelated to the quote.
const contextLen = 32;
```

### B.4 我们的实现 vs Hypothesis（逐项对照）

| 维度 | 我们的 `core/perch-epub/src/anchor.rs` | Hypothesis | 点评 |
|---|---|---|---|
| 度量 | 精确子串，失败才退空白容忍 | **编辑距离**，允许 `len/2` 个错 | 它更宽容，能吃"改了一个标点/错字" |
| 上下文长度 | **无上限** | 固定 **32 字符** | 前文越长越易误命中无关区域 |
| 位置先验 | **无** | hint 权重 2/92 | **最该补的一块** |
| 多处命中无上下文 | **返回 `None`** | 仍取最高分（靠 hint + 前后文区分） | 补上 hint 后就没必要这么保守 |
| 阈值 | `MIN_CONFIDENCE = 0.6` 硬阈值 | **`matchQuote` 里根本没有阈值** | 它把"正确性"交给下一节的 selector 阶梯 |
| 评分结构 | `0.5 + 0.25·前文 + 0.25·后文`，另有 `occurrence_count` 特判（唯一 0.8 / 多处 0.4） | 50/20/20/2 线性加权，无特判 | 我们的 `occurrence_count` 特判是**隐式先验**，不如显式 hint 干净 |

### B.5 最值得抄的：selector 阶梯 + assertion

`html.ts` 的 `anchor()`：

```ts
// 从简单到复杂依次 fallback
RangeSelector → TextPositionSelector → TextQuoteSelector → MediaTimeSelector

const maybeAssertQuote = (range: Range) => {
  if (quote?.exact && range.toString() !== quote.exact) {
    throw new Error('quote mismatch');   // ← 断言失败就降级到下一级
  }
  return range;
};
```

即：**用便宜的定位器先试，用存下来的原文当断言去校验，不通过才退到昂贵的模糊搜索。**
比"一次模糊匹配 + 阈值"稳，因为**每一级都有明确的证伪条件**。
我们已经存了 `text.before / highlight / after`，加这一步成本很低。

### B.6 问题 B 的建议

1. **加 position hint**：`AnchorQuery` 增一个 `hint: Option<u64>`（字符偏移），从 CFI/progression 换算得来；
   打分公式加一项 `+ 2/92 * (1 - |start - hint| / doc_len)`。
2. **`contextLen` 固定为 32**，超出截断，别再让前文无限长。
3. **加 selector 阶梯**：先用 CFI 直接定位 → 断言 `highlight` 是否吻合 → 失败再走模糊匹配。
4. **可以保留 0.6 阈值**（我们的"宁缺毋滥"取向合理），但有了 hint 之后，
   `occurrence_count` 那个特判可以删掉，换成显式 hint 项，逻辑更干净。
5. 空白容忍回退**保留**——这是我们的优势项。

## 四、问题 C：CFI 与 Readium 的互操作性

### C.1 规范原文：范围 CFI 的准确语义

CFI 规范语法（IDPF，EBNF 原文）：

```
fragment        = "epubcfi(", ( path, [ range ] ), ")" ;
path            = step, local_path ;
range           = ",", local_path, ",", local_path ;      ← 两个逗号，三段式
local_path      = { step }, ( redirected_path | [ offset ] ) ;
redirected_path = "!", ( offset | path ) ;
step            = "/", integer, [ "[", assertion, "]" ] ;
offset          = ( ( ":", integer )
                  | ( "@", number, ":", number )
                  | ( "~", number, [ "@", number, ":", number ] ) ), [ "[", assertion, "]" ] ;
```

**"相对父路径展开"的权威规则**（规范正文原文）：

> "A range is a path followed by **two local (or relative) paths** that identify the start and end
> of the range. ... **each start and end subpath must be concatenated to the parent path** to create
> the start location path (PS) and end location path (PE)."

所以展开就是**字符串拼接**：

```
epubcfi( /6/4!/4/2 , /10/2 , /12/4 )
         └─ parent ─┘  └start┘  └ end┘

start = /6/4!/4/2 + /10/2  =  /6/4!/4/2/10/2
end   = /6/4!/4/2 + /12/4  =  /6/4!/4/2/12/4
```

**两条容易漏的**：
- `local_path = { step }, ...` —— `{step}` 允许**零个 step**，所以 start/end 可以只有 offset。
- `redirected_path` 允许 start/end **自带 `!`**。

规范还有两条明确否定：

> "It is **not valid** to use a path to an element as a shorthand for the range from the beginning
> to the end of the element. Single path notation always denotes a **location point**."
>
> "If range is used where single location is expected by the context, the **start location must be used**."

**→ 没有官方两段式**，`epubcfi(a,b)` 不是合法 range。

### C.2 Readium 的 `partialCfi` 到底是什么

`readium/swift-toolkit@3.11.0` `Sources/Shared/Publication/Extensions/HTML/Locator+HTML.swift` 原文注释：

```swift
/// `partialCFI` is an expression conforming to the **"right-hand" side** of the EPUB CFI syntax,
/// that is to say: **without the EPUB-specific OPF spine item reference that precedes the first !**
/// exclamation mark (which denotes the "step indirection" into a publication document). Note
/// that **the wrapping `epubcfi(***)` syntax is not used** for the `partialCFI` string, i.e.
/// the "fragment" part of the CFI grammar is ignored.
var partialCFI: String? { otherLocations["partialCfi"]?.string }
```

`flutter_readium` 的 Dart 模型逐字抄了同一段（`flutter_readium_platform_interface/lib/src/shared/publication/locator.dart:448`）。

**⚠️ 发现一处现存错误**——`dart/perch_core/tool/ffi_smoke.dart:82`：

```dart
'locations': {'progression': 0.42, 'partialCfi': '/6/4!/4/2'},
//                                                ^^^^^^^^^^ 含 spine 引用 和 `!`
//                                                按 Readium 契约这不是合法 partialCfi
```

按契约应该是 **`'/4/2'`**（`!` 之后的部分）。建议改掉，否则这个值真流到 Readium 里会被当成非法 partial CFI。

### C.3 ❗ 最反直觉的发现：Readium 现代工具链根本不生成 CFI

逐个 grep 实际渲染/导航代码：

| 仓库 / 版本 | 文件 | 含 "cfi" 次数 |
|---|---|---|
| `readium/swift-toolkit@3.11.0` | `Sources/Navigator/EPUB/Assets/Static/scripts/readium-reflowable.js`（104 KB） | **0** |
| `readium/swift-toolkit@3.11.0` | `EPUBNavigatorViewModel.swift` | **0** |
| `readium/swift-toolkit@3.11.0` | `EPUBReflowableSpreadView.swift` | **0** |

Swift 侧 reflowable JS 实际产出的是 `cssSelector`（6 处）与 `progression`（2 处）。

**对我们的影响，比原先估计的好：**

   这反而更可控。
3. 真正要担心的是**别的阅读器**（Apple Books / Calibre 等）导出的 CFI 导入我们库时的兼容性。

> **建议把这条写进 `docs/02-架构设计.md`，从"风险"改列为"已确认事实"。**

### C.4 epub.js 的三个坑（要互通就得避）

`futurepress/epub.js` `src/epubcfi.js`：

**坑 1：`toString()` 无条件输出 `!`** —— 即使没有间接引用：

```js
toString() {
  var cfiString = "epubcfi(";
  cfiString += this.segmentString(this.base);
  cfiString += "!";                    // ← 永远加
  cfiString += this.segmentString(this.path);
  ...
}
```

纯包内路径会变成 `epubcfi(/6/4!/)` 这种形状。

**坑 2：分段用裸 `split(",")`** —— assertion 里带逗号就崩：

```js
getRange(cfiStr) {
  var ranges = cfiStr.split(",");      // 不认得 [...] 里的逗号
  if (ranges.length === 3) { return [ranges[1], ranges[2]]; }
  return false;                        // 只认三段式
}
```

**坑 3：assertion 用正则抠** —— 转义过的 `^]` 会破坏匹配：

```js
var assertion = termialStr.match(/\[(.*)\]/);
```

规范要求 `[` `]` `^` `,` `(` `)` `;` `=` 都要用 `^` 转义，而 epub.js 的往返对这些字符**不保真**。

**→ 结论：和 epub.js 互通时，断言里不要放特殊字符，宁可放纯 id。**

### C.5 问题 C 的建议

1. **把 `partialCfi` 的口径定死**（`!` 右侧、无 `epubcfi()` 包装），并修掉 `ffi_smoke.dart:82` 的值。
2. 范围 CFI 展开按规范实现为**字符串拼接**（`parent + start_local`），**不要**自己想"共同祖先省略"。
3. 支持 `{step}` 为空、start/end 自带 `!` 这两种边界。
4. 把 C.3 的结论写进架构文档，CFI 权威版本 = 我们自己。

## 五、问题 D：iOS 静态库链接

### D.1 `DynamicLibrary.process()` 选对了吗？——对，但要理解前提

Dart SDK 源码原文（`sdk/lib/ffi/dynamic_library.dart`）：

```dart
/// Creates a [DynamicLibrary] holding all **global symbols**.
///
/// Any symbol in a library currently loaded with global visibility
/// (including the executable itself) may be resolved through this library.
external factory DynamicLibrary.process();

/// Creates a [DynamicLibrary] containing all the symbols of the **running executable**.
///
/// This is useful for using dart:ffi with **static libraries**.
external factory DynamicLibrary.executable();
```

**注意官方把 `executable()` 标注为 "useful for static libraries"**。选哪个取决于 `.a` 最终链到哪：

| 链接方式 | 该用哪个 |
|---|---|
| cargokit（`-force_load` 进**插件 framework**） | **`process()`** ✅ 我们现在是对的 |
| 手工链进主可执行文件 | `executable()` |

`flutter_readium` 走 CocoaPods/SPM，插件是**动态 framework**，所以 `process()` 正确。
我们 `dart/perch_core/lib/perch_core.dart` 里那句注释「iOS：静态链接后符号在进程内」是准确的说法。

### D.2 `-force_load` 是必须的，位置很明确

cargokit 官方教程（`matejknopp.com/post/flutter_plugin_in_rust_with_no_prebuilt_binaries/`）的 podspec 配方原文：

```ruby
s.source       = { :path => '.' }
s.source_files = 'Classes/**/*'

s.script_phase = {
  :name => 'Build Rust library',
  # 第一个参数是 rust 目录的相对路径，第二个是库名
  :script => 'sh "$PODS_TARGET_SRCROOT/../cargokit/build_pod.sh" ../rust hello_rust_ffi_plugin',
  :execution_position => :before_compile,
  :input_files  => ['${BUILT_PRODUCTS_DIR}/cargokit_phony'],
  # 让 Xcode 知道 -force_load 引用的 .a 是这个 build step 产出的
  :output_files => ["${BUILT_PRODUCTS_DIR}/libhello_rust_ffi_plugin.a"],
}

s.pod_target_xcconfig = {
  'DEFINES_MODULE' => 'YES',
  'EXCLUDED_ARCHS[sdk=iphonesimulator*]' => 'i386',
  'OTHER_LDFLAGS' => '-force_load ${BUILT_PRODUCTS_DIR}/libhello_rust_ffi_plugin.a',
}
```

**四个要点**：
1. `-force_load` 加在**插件自己的 `pod_target_xcconfig['OTHER_LDFLAGS']`**，**不是 app 的 xcconfig**。
   因为 `perch_call` 没有任何 Swift/ObjC 代码引用它，不加就会被链接器当死代码丢掉。
2. `script_phase` **必须 `:execution_position => :before_compile`**，并声明 `input_files` / `output_files`，
   否则 Xcode 不知道依赖关系，会偶发地"先链接后编译"。
3. 路径是 `$PODS_TARGET_SRCROOT/../cargokit/build_pod.sh`，两个参数：rust 目录相对路径 + 库名。
4. 教程推荐 `ln -s macos ios`，一份 podspec 同时服务两个平台。

### D.3 cargokit 内部到底做什么（读源码确认）

`build_tool/lib/src/build_pod.dart`：

```dart
final targets = Environment.darwinArchs.map((arch) =>
    Target.forDarwin(platformName: Environment.darwinPlatformName, darwinAarch: arch)).toList();
...
if (staticLibs.isNotEmpty) {
  final finalTargetFile = path.join(outputDir, "lib$libName.a");
  performLipo(finalTargetFile, staticLibs.map((e) => e.path));   // lipo -create 合并多架构
}
```

- **多架构用 `lipo -create` 合并成一个 fat `.a`，不是 xcframework**
  （`CARGOKIT_DARWIN_ARCHS=$ARCHS` 由 Xcode 传入，真机 arm64 / 模拟器 arm64 / 模拟器 x86_64 各自构建时合并）。
- 产物落在 `CARGOKIT_OUTPUT_DIR = $PODS_CONFIGURATION_BUILD_DIR/$PRODUCT_NAME`。
- **cargokit 自己不负责 `-force_load`**——那是插件作者在 podspec 里写的（D.2 那份配方）。
- 通过环境变量驱动：`CARGOKIT_DARWIN_PLATFORM_NAME=$PLATFORM_NAME`、`CARGOKIT_DARWIN_ARCHS=$ARCHS`、
  `CARGOKIT_CONFIGURATION=$CONFIGURATION`、`CARGOKIT_MANIFEST_DIR=$PODS_TARGET_SRCROOT/$1`。
- 配置文件：Rust crate 旁的 `cargokit.yaml`（toolchain / `extra_flags` / `precompiled_binaries`）、
  app 根目录的 `cargokit_options.yaml`（`verbose_logging` / `use_precompiled_binaries`）。
- **硬依赖 Rustup**：README 原文 *"On macOS it will also detect a homebrew Rust installation in PATH
  and will prompt user to call `brew unlink rust` first"*，因为要交叉编译。

### D.4 我们这套架构特有的一个坑

`flutter_readium` 的 iOS 用的是 **Swift Package Manager**
（`ios/flutter_readium/Package.swift`，`swift-tools-version: 5.9`，依赖 `swift-toolkit.git` 3.11.0）。

而 **cargokit 的 iOS 路径只有 CocoaPods**（`build_pod.sh` + podspec `script_phase`），没有 SPM build plugin。所以：

- Flutter 支持 SPM 与 CocoaPods **混用**，我们的 Rust 插件走 CocoaPods 即可，
  但 `Podfile` / `pod install` 会一直留在构建回路里，别忘了。
- **不能**把 Rust 静态库塞进 `flutter_readium` 的 SPM target（除非自己写 SPM build tool plugin，成本高）。

### D.5 没有 Mac 时能预先验证到什么程度

| 能在 Linux 做 | 只能 macOS 做 |
|---|---|
| `cargo build -p perch-ffi --target aarch64-apple-ios`（toolchain 已配好 3 个 target） | `lipo -create` 合并后在 podspec 里被正确引用 |
| `cargo test` / FFI 冒烟（`.so`，**已完成**） | `xcodebuild -sdk iphoneos` 验证 `-force_load` 不报重复符号 |
| **`nm` 检查符号导出**（见下） | 运行时 `DynamicLibrary.process()` 真能解析到符号 |
| `cargo build --target aarch64-apple-ios-sim` 验证无 C 依赖 | 真机 / 模拟器实际跑起来 |

**建议加进 CI 的一条零成本断言**：编译完 `aarch64-apple-ios` 静态库后，检查两个符号是**全局外部符号**：

```bash
llvm-nm --defined-only -g core/target/aarch64-apple-ios/release/libperch_ffi.a \
  | grep -E '_perch_call|_perch_string_free'
# 期望看到 T（全局可导出），而不是 t（局部）或 U（未定义）
```

这条能在 Linux 上跑，能提前抓住"符号没导出 / 被优化掉"这类问题。

### D.6 问题 D 的建议

1. 新建一个 CocoaPods 包装插件（不要往 `flutter_readium` 里塞），按 D.2 的配方写 podspec。
2. 把 cargokit 作为 subtree 引入（pub 不支持 git 依赖的 submodule）。
3. Rust crate 旁放 `cargokit.yaml` 固定 toolchain，保证与 `core/rust-toolchain.toml` 一致。
4. CI 里加 D.5 的 `nm` 断言。
5. 注意 `-force_load` 一个含 std 的 Rust 静态库可能带来**重复符号**风险——
   如果将来有第二个 Rust 静态库，需要评估（目前只有一个，无此问题）。

### 执行中额外发现的两个真问题（报告中未提及）

**① `just build-ios-lib` 配方一直是坏的。**

`perch-ffi` 声明了 `crate-type = ["cdylib", "staticlib", "rlib"]`。在 Linux 上交叉编译到
iOS 时，**cdylib 必然失败**（要链接，而 Linux 的 `cc` 不认识 `-target arm64-apple-ios`），
于是整个 `cargo build --target aarch64-apple-ios` 以非零退出码结束 —— 尽管 staticlib
其实已经产出。表现为"命令报错但产物存在"，很容易被误判为成功。

修法：改用 `cargo rustc --crate-type staticlib` 覆盖 crate-type，只做静态库。

**② `set -o pipefail` + `grep -q` 的组合会误报失败。**

`nm ... | grep -q` 中，`grep -q` 一命中就退出、关闭管道，`nm` 收到 SIGPIPE 非零退出，
在 `pipefail` 下整条管道被判失败 —— **匹配成功却报失败**。
修法：先把输出存进变量再 `grep`（`symbols=$(...); grep -q ... <<<"$symbols"`）。

> 这两个坑都印证了 §D.5 的价值：把"能在 Linux 上做的检查"真正做成断言，
> 才可能在没 Mac 的情况下提前发现构建问题。

### 对 §三 的一处有意偏离

报告 §B.6 建议采用 Hypothesis 的 `50/20/20/2` 权重。实现时改为**等权重四证据模型**
（命中原文 0.5 + 前文/后文/位置先验各 0.25）。原因：Hypothesis 的 quote 项是
`1 - errors/len` 的**连续值**（基于编辑距离），而我们的 quote 项是**二值**的
（精确命中，否则走空白容忍回退）。拿 50/92 套到一个二值项上会让"精确命中"独占 54%，
与它的语义不可比。

**保留的是结构（四类证据 + hint 作先验），不照搬不可比的数值。**
