## 三、已决策事项（含理由，不要重复讨论）

| 决策 | 理由 |
|---|---|
| **UI = Flutter** | 无 Mac，原生 SwiftUI 无法验证 |
| **手写 C ABI + JSON 契约**，不用 flutter_rust_bridge | FRB 只能写不能验；手写 ABI 可在 Linux 用 `dart:ffi` 加载 `.so` 端到端验证。契约稳定，将来换 FRB 只换传输层 |
| **卷页自绘**，不用 `page_curl_flip` | `CurlOverlay` 几何写死全宽左右剥页、无手指坐标入参 → 做不了角拖拽，与 Rust 几何互斥（见 `docs/09` §A.5） |
| **不引入 cargokit** | 自写 `build_rust.sh` 更透明，需求只需「按 target 编译 + lipo」 |
| **索引格式自定义**（delta+varint） | 倒排是升序整数序列，比 bincode 省一个数量级 |
| **标注评分用等权重四证据模型** | 有意偏离 Hypothesis 的 50/20/20/2：它的 quote 项是编辑距离连续值，我们是二值，数值不可比（见 `docs/09` §八） |
| **同步不自建服务器**，用 CloudKit 私有库 | 用户 2026-10-17 拍板。省掉 axum/鉴权/多租户/服务端持久化一整块；代价：只做 Apple 端 + 占用户 iCloud 配额，见 `docs/04` #8 |
| 最低 iOS 18.0 | `flutter_readium` 要求 ≥15；按产品决策取 18 |
| 存储当前用 JSON 文件 | 过渡实现，接口 `ProgressStore` 不变，最终换 SQLite |
| 同步 = **合并引擎** + CloudKit 传输 | ✅ 2026-10-17 决策：**不自建服务器**，传输层用 **CloudKit 私有库**，合并仍在设备端 Rust（HLC 字段级 LWW，时间戳存进记录字段），书文件走 `CKAsset`，只做 Apple 端。`perch-sync::SyncServer`（纯内存）降级为**测试替身**。⚠️ 跨设备主键必须用 `fingerprint` 而不是 `BookId`（后者是随机 UUID）。见 `docs/04` #8、`docs/02` §八点二 |

### 当时的现象（第 17~19 轮的历史快照；**现已修复**，结论见本节最后一小节）

```
编译 iOS（模拟器）           ✓ success
断言 Rust 符号已链入 App 二进制 ✗ failure
```

即：**编译通过，但 `_perch_call` / `_perch_string_free` 不在 `Runner` 二进制里**。
（事后确认：符号确实不在 `Runner` 里，而在 `Runner.debug.dylib` 里——断言当时查错了文件。）

### 为什么这条断言重要

`perch_call` 没有任何 Swift/ObjC 代码引用，默认会被链接器当死代码丢掉，
而 **App 依然「编译成功」**，直到运行时 `DynamicLibrary.process()` 才报符号找不到。
「编译通过 ≠ 可用」。

### 已尝试过（**当时**都还没解释现象；后已定位，见下面第 17~20 轮）

1. `pod_target_xcconfig` 里写 `-force_load ${BUILT_PRODUCTS_DIR}/libperch_ffi.a`
   （**无效**：pod target 的参数到不了 App 的链接命令行；正确位置是 `user_target_xcconfig`＋带 `perch_core_ffi/` 的路径）
2. 加 C 链接锚点 `perch_link_anchor.c` + Swift 侧 `@_silgen_name` 调用

### 根因已定位：断言脚本自己静默死亡（2026-10-17）

**`gh` 命令行早就已登录**（`gh auth status` 显示 `Sycamore-awa`），
所以 `gh run view <run_id> --log` 一直可用 —— 之前"日志接口需认证拿不到"
的判断是错的，白白多推了两轮 CI。**教训：先 `gh auth status` 再谈拿不到日志。**

真实日志（run #16，步骤耗时 2 秒后退出码 1，无任何输出）指向这一行：

```bash
perch=$(grep -i 'perch' <<<"$symbols" | head -6 | tr '\n' '|')
```

`head -6` 读满 6 行就退出 → `grep` 收 SIGPIPE → `pipefail` 让整条管道失败
→ `bash -e` 中止**赋值语句本身** → 后面的 `echo "::error::..."` 一行都没执行。

所以 `::error::` 注解没出现**不是注解机制的问题，是它根本没被调用**。
「修 `find | head` 加 `|| true`」时只修了上一行，**紧邻的下一行是同一个 bug**
—— 同类坑第 4 次。

已修：断言脚本重写为**不含任何"消费端提前退出"的管道**，
诊断全部 `echo` 到 stdout，并在失败时额外 dump 四项排查信息
（库内符号 / 各 xcconfig 里的 force_load / Runner.app 内容 / 构建模式）。
本地用假二进制跑过通过与失败两条路径。

    OTHER_LDFLAGS = $(inherited) -force_load ${BUILT_PRODUCTS_DIR}/libperch_ffi.a

app/build/ios/Debug-iphonesimulator/     ← 目录在，但没有 .a

**关键推理：假设 1 被证实，且不是猜的。**
如果 `-force_load .../libperch_ffi.a` 真的作用在 App 的链接命令行上，
而那个文件并不存在，链接就应该**直接报错失败**。但 App 链接成功了
⇒ 这条参数根本没到达 App 的链接器。旁证：它只出现在 `perch_core_ffi.*.xcconfig`
（pod target），不在 `Pods-Runner.*.xcconfig`（App）里。

**第二个 bug：`libperch_ffi.a` 压根没生成。**
`app/build/ios/Debug-iphonesimulator/` 目录存在但没有 `.a`，
说明 podspec 的 `Build Rust core` 脚本阶段**没跑**（或产物落到了别处）。

**第三个 bug（顺带发现，此前没注意到）：**
CI 的 rustup 安装写的是 `--default-toolchain none`，
`~/.cargo/bin/cargo` 只是 rustup 代理，`command -v cargo` 能通过，
但真执行会报 "no default toolchain configured"。
而且从没装过 `aarch64-apple-ios-sim` 这个 target 的 std。

### 第 18 轮：真正的原因只是**路径少了一层目录**

上一轮的四项修正都生效了（`-force_load` 终于出现在 App 的链接命令行、
cargo 1.99.1 可用、全量日志拿到），然后失败点前移到「编译 iOS」本身：

```
Error (Xcode): Build input file cannot be found:
  '.../app/build/ios/Debug-iphonesimulator/libperch_ffi.a'.
  Did you forget to declare this file as an output of a script phase ...?
```

而 `if: always()` 诊断步骤同时给出了库的真实位置：

```
① 仓库里所有 libperch_ffi.a ----
./app/build/ios/Debug-iphonesimulator/perch_core_ffi/libperch_ffi.a
④ App 侧 OTHER_LDFLAGS ----
OTHER_LDFLAGS = $(inherited) -framework "perch_core_ffi" -force_load ${BUILT_PRODUCTS_DIR}/libperch_ffi.a
```

**库一直在生成，只是 `BUILT_PRODUCTS_DIR` 有两个不同的值：**

| 上下文 | `${BUILT_PRODUCTS_DIR}` |
|---|---|
| podspec 的 script_phase（**pod target** 里跑） | `.../Debug-iphonesimulator/`**`perch_core_ffi/`** |
| `user_target_xcconfig`（**App target**） | `.../Debug-iphonesimulator/` |

所以脚本写到的位置和 `-force_load` 找的位置差了一层 `perch_core_ffi/`。
→ 修法：`-force_load ${BUILT_PRODUCTS_DIR}/perch_core_ffi/libperch_ffi.a`。

**顺带纠正两个我之前的错误判断：**

1. **`perch_core_ffi` 是动态 framework，不是静态库。**
   `OTHER_LDFLAGS` 里是 `-framework "perch_core_ffi"`（静态库会是 `-l"..."`），
   因为 Flutter 生成的 Podfile 默认带 `use_frameworks!`。
   所以「静态库 pod 没有链接步骤」这个理由不成立；
   `-force_load` 必须写进 `user_target_xcconfig` 的真正原因，
   是 pod_target 的链接参数不会出现在 App 的链接命令行上。
2. **第 17 轮「库没产出」是误判** —— 我的 `find`/glob 只查了 `app/build/ios/*/`，
   没查 `*/*`。这正是本轮加 `if: always()` 诊断步骤的价值：
   同一个问题换个问法就一眼看穿，比再猜一轮便宜得多。

### 第 19 轮：链接成功了，但断言查错了文件

路径修对后 `编译 iOS（模拟器）`**通过**，失败点回到符号断言。但关键现象是：

```
Runner: 字节数 123792，符号数 123
```

**这个数字在第 17、18、19 轮完全一样** —— 即使第 19 轮 `-force_load` 已经
带着正确路径生效、`.a` 也确实存在，`Runner` 一个字节都没变。
且 `Runner.app/` 里还有一个 `__preview.dylib`。

⇒ **`Runner` 不是承载我们链接参数的那个产物**（Flutter 新版模拟器构建里
主二进制只是薄壳）。「`nm Runner` 里没有 `_perch_call`」并不等于符号没链进来
—— 前几轮的断言一直在看错的文件。

**已改**：断言改为遍历 app bundle 里**所有** Mach-O（用 `file -b` 判类型），
任一镜像里同时出现两个符号即通过，并打印符号所在文件；失败时额外 `otool -L`
看动态依赖、`find` 出 `.a` 并检查库内符号。本地用假 bundle + `file` shim
验过「符号在 Runner / 在 Framework / 哪儿都没有」三条路径。

**这条断言的局限（诚实标注）**：它证明「符号在 bundle 里」，
不等于「运行时 `DynamicLibrary.process()` 一定解析得到」——
后者仍需真机/模拟器实际启动 App 才能验证（见 §五 未验证清单）。

### 第 20 轮：全绿，以及最终确认的链接结构

CI 三个 job 全绿。断言给出的符号分布：

```
Runner.app/Runner                              123 行 nm 输出   ← 薄壳启动器
Runner.app/__preview.dylib                     1 行             ← 空
Runner.app/Runner.debug.dylib                  90197 行         ★ Rust 核心在这里
Runner.app/Frameworks/perch_core_ffi.framework 101 行           ← 只有 Swift 壳
```

`Runner.debug.dylib` 里同时有 `T _perch_call`、`T _perch_string_free`，
以及 `perch_import` / `perch_index` / `perch_ffi` 的 mangled 符号；
framework 里只有 `PerchCoreFfiPlugin` 的 Swift 符号。

**这才是正确的结构**：

| 层 | 内容 |
|---|---|
| `Runner.debug.dylib`（App 主镜像） | Rust 核心，由 `user_target_xcconfig` 的 `-force_load` 链入 |
| `perch_core_ffi.framework` | 只有 `PerchCoreFfiPlugin.swift` 这一层空壳（CocoaPods 需要它来触发集成） |

主镜像启动即加载 ⇒ `DynamicLibrary.process()` 能解析到这两个符号。

### 这一条卡点的完整教训

1. **没有日志就不要改代码**。（`gh` 其实一直是登录状态，白推了两轮）
2. **「编译通过」和「符号在里」是两件事**，而「在哪个文件里」是第三件事。
   断言写死 `nm Runner` 是这次绕圈最久的原因 —— 应该先枚举再断言。
3. **同一个路径变量在不同 target 里含义不同**（`BUILT_PRODUCTS_DIR`）。
4. 诊断脚本本身要能「活着把话说出来」：SIGPIPE 那一类 bug 让失败变成哑巴，
   这是最贵的故障形态。

### ⚠️ 下一个已知风险：Flutter 正在转向 SPM

构建日志里明确警告：

```
The following plugins do not support Swift Package Manager for ios:
  - perch_core_ffi
This will become an error in a future version of Flutter.
```

即 CocoaPods 集成方式**将来会失效**。现在不是失败原因，但需要关注；
届时要么给插件加 `Package.swift`，要么改用 Flutter 的 SPM 插件集成方式。

## 六、踩过的坑（SIGPIPE 那一类踩了 4 次，务必先读这节）

### 6.1 CI / 平台

| 坑 | 现象 | 修法 |
|---|---|---|
| `runs-on: macos-26-arm64` 不存在 | job **永久 queued 且不报错**（比失败更难察觉） | 用 `macos-26`（标准 runner 标签不带 `-arm64`） |
| 中文项目路径 | `flutter analyze` 抛 `FormatException`（LSP 的 `Content-Length` 按字节算） | 用 `dart analyze`；CI 路径是 ASCII 不受影响 |
| `.gitignore` 里有 `*.xcodeproj/` | **Xcode 工程没进仓库**，CI 检出后无法构建 | 已移除；`flutter create` 生成的工程必须提交 |
| 本地 PATH 上有 `llvm-nm`（`/usr/bin/llvm-nm`，属 llvm 包），CI 上默认只有 GNU nm（binutils） | GNU nm 对 Mach-O 报 `file format not recognized`，本地绿 CI 红 | 显式探测 `llvm-nm`（含 `/usr/lib/llvm-*/bin`）+ CI 设 `PERCH_REQUIRE_LLVM_NM=1`。⚠️ 原文写"本地 `/usr/bin/nm` 是 llvm-nm"——2026-10-17 复核：`/usr/bin/nm` 属 binutils，`llvm-nm` 是另一个可执行文件 |
| 单个 `just ci` 步骤 | 失败时只知「有东西坏了」 | 已拆成独立步骤，**失败步骤名即定位** |
| 连续推送会**取消**上一轮的 iOS job | `gh run list` 里显示 `X`，和真失败长得一样，容易误判 | 看 annotation 是否写着 `Canceling since a higher priority waiting request`；每个提交的 iOS 结论只对**最后一次**推送有效 |
| **macOS 的 bash 3.2 会把变量名后面的中文算进变量名**（2026-10-18，模拟器冒烟第一次跑就挂在它上面） | 现象：`line 79: console_log<乱码>: unbound variable`。根因：macOS 自带 `/bin/bash` 是 **3.2**，不是 UTF-8 感知的；写成 `$var）`（后面紧跟全角括号）时，多字节字符被当成变量名的一部分。**Linux 的 bash 5 完全不会暴露这个问题**，本地 harness 全绿也拦不住 | 一律写 `${var}` 或加空格/逗号隔开；`core-linux` job 加了静态检查（`grep -P '\$[A-Za-z_][A-Za-z0-9_]*(?=[^\x00-\x7F])'`），`tools/test_simulator_smoke.sh` 里也有一份。⚠️ 推论：**CI 脚本的新写法在 Linux 上跑通 ≠ 在 macOS 上跑通**，凡涉及 bash 版本/编码的假设都要在 CI 上验 |

### 6.2 Shell（**同一类坑踩了 4 次**）

| 坑 | 说明 |
|---|---|
| `nm ... \| grep -q` | `grep -q` 命中即退出关管道 → `nm` 收 SIGPIPE → `pipefail` 判失败，**匹配成功却报失败** |
| `find ... \| head -1` | 同上，且**掩盖了 C 锚点的真实效果** |
| `grep ... \| head -6` | **第 4 次**。修上一行时紧邻的下一行也是同一个 bug，导致断言步骤 2 秒静默退出、诊断一行没打印，害我以为「注解机制坏了」 |
| 管道吞退出码 | Actions 默认 `bash -e` **不含** `pipefail`，`cmd \| tail` 会让步骤永远绿 |

**纪律**：CI 脚本里每个管道都要显式想一遍退出码；需要"提前退出"的消费者（`grep -q`、`head`）
一律先取全量到变量，或加 `|| true`。
