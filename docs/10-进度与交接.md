## 三、已决策事项（含理由，不要重复讨论）

| 决策 | 理由 |
|---|---|
| **UI = Flutter** | 无 Mac，原生 SwiftUI 无法验证 |
| **手写 C ABI + JSON 契约**，不用 flutter_rust_bridge | FRB 只能写不能验；手写 ABI 可在 Linux 用 `dart:ffi` 加载 `.so` 端到端验证。契约稳定，将来换 FRB 只换传输层 |
| **卷页自绘**，不用 `page_curl_flip` | `CurlOverlay` 几何写死全宽左右剥页、无手指坐标入参 → 做不了角拖拽，与 Rust 几何互斥（见 `docs/09` §A.5） |
| **不引入 cargokit** | 自写 `build_rust.sh` 更透明，需求只需「按 target 编译 + lipo」 |
| **索引格式自定义**（delta+varint） | 倒排是升序整数序列，比 bincode 省一个数量级 |
| **标注评分用等权重四证据模型** | 有意偏离 Hypothesis 的 50/20/20/2：它的 quote 项是编辑距离连续值，我们是二值，数值不可比（见 `docs/09` §八） |
| 最低 iOS 18.0 | `flutter_readium` 要求 ≥15；按产品决策取 18 |
| 存储当前用 JSON 文件 | 过渡实现，接口 `ProgressStore` 不变，最终换 SQLite |
| 同步无服务端 | 只有合并引擎，wire protocol 未做 |

### build_rust.sh 已在本机真实验证（三个分支）

| 场景 | 结果 |

### 现在的现象

```
编译 iOS（模拟器）           ✓ success
断言 Rust 符号已链入 App 二进制 ✗ failure
```

即：**编译通过，但 `_perch_call` / `_perch_string_free` 不在 `Runner` 二进制里**。

### 为什么这条断言重要

`perch_call` 没有任何 Swift/ObjC 代码引用，默认会被链接器当死代码丢掉，
而 **App 依然「编译成功」**，直到运行时 `DynamicLibrary.process()` 才报符号找不到。
「编译通过 ≠ 可用」。

### 已尝试过（都还没解释现象）

1. `pod_target_xcconfig` 里写 `-force_load ${BUILT_PRODUCTS_DIR}/libperch_ffi.a`
2. 加 C 链接锚点 `perch_link_anchor.c` + Swift 侧 `@_silgen_name` 调用

### 根因已定位：断言脚本自己静默死亡（2026-10-17）

**`gh` 命令行早就已登录**（`gh auth status` 显示 `Sycamore-awa`），
所以 `gh run view <run_id> --log` 一直可用 —— 之前"日志接口需认证拿不到"
的判断是错的，白白多推了两轮 CI。**教训：先 `gh auth status` 再谈拿不到日志。**

真实日志（run #16，步骤耗时 2 秒后退出码 1，无任何输出）指向这一行：

```bash
perch=$(grep -i 'perch' <<<"$symbols" | head -6 | tr '\n' '|')
```

`head -6` 读满 6 行就退出 → `grep` 收 SIGPIPE → `pipefail` 让整条管道失败
→ `bash -e` 中止**赋值语句本身** → 后面的 `echo "::error::..."` 一行都没执行。

所以 `::error::` 注解没出现**不是注解机制的问题，是它根本没被调用**。
「修 `find | head` 加 `|| true`」时只修了上一行，**紧邻的下一行是同一个 bug**
—— 同类坑第 4 次。

已修：断言脚本重写为**不含任何"消费端提前退出"的管道**，
诊断全部 `echo` 到 stdout，并在失败时额外 dump 四项排查信息
（库内符号 / 各 xcconfig 里的 force_load / Runner.app 内容 / 构建模式）。
本地用假二进制跑过通过与失败两条路径。

### 第 17 轮拿到真实数据：两个**独立**的 bug

修好脚本后第一次拿到有效诊断（run #17）：

```
二进制: app/build/ios/iphonesimulator/Runner.app/Runner
字节数: 123792   符号数: 123
---- 所有含 perch 的符号 ----
（没有任何含 perch 的符号）
---- ① libperch_ffi.a 本身有符号吗 ----
  没找到 libperch_ffi.a —— 构建阶段没产出
---- ② force_load 在哪 ----
命中: Pods/Target Support Files/perch_core_ffi/perch_core_ffi.debug.xcconfig
    OTHER_LDFLAGS = $(inherited) -force_load ${BUILT_PRODUCTS_DIR}/libperch_ffi.a
---- ④ 构建模式 ----
app/build/ios/Debug-iphonesimulator/     ← 目录在，但没有 .a
app/build/ios/iphonesimulator/
```

**关键推理：假设 1 被证实，且不是猜的。**
如果 `-force_load .../libperch_ffi.a` 真的作用在 App 的链接命令行上，
而那个文件并不存在，链接就应该**直接报错失败**。但 App 链接成功了
⇒ 这条参数根本没到达 App 的链接器。旁证：它只出现在 `perch_core_ffi.*.xcconfig`
（pod target），不在 `Pods-Runner.*.xcconfig`（App）里。

**第二个 bug：`libperch_ffi.a` 压根没生成。**
`app/build/ios/Debug-iphonesimulator/` 目录存在但没有 `.a`，
说明 podspec 的 `Build Rust core` 脚本阶段**没跑**（或产物落到了别处）。

**第三个 bug（顺带发现，此前没注意到）：**
CI 的 rustup 安装写的是 `--default-toolchain none`，
`~/.cargo/bin/cargo` 只是 rustup 代理，`command -v cargo` 能通过，
但真执行会报 "no default toolchain configured"。
而且从没装过 `aarch64-apple-ios-sim` 这个 target 的 std。

**已做的修正（下一轮验证）**

| 修正 | 原因 |
|---|---|
| podspec：`-force_load` 移到 `user_target_xcconfig` | 只有它会写进 App 的 xcconfig |
| CI：rustup 改成 `--default-toolchain stable` + `rustup target add aarch64-apple-ios aarch64-apple-ios-sim` | 让 cargo 真的能编 |
| CI：构建步骤不再 `| tail -200`，全量日志落盘后 grep 关键行 | 上一轮 258s 的构建日志只剩 29 行，把「脚本阶段有没有跑」直接丢掉了 |
| CI：新增 `if: always()` 诊断步骤：`find` 全仓 `libperch_ffi.a`、dump `Pods-Runner` 的 `OTHER_LDFLAGS`、查 `Podfile.lock` | 一次把「库在哪、参数在哪」问清楚 |
| podspec 头部注释同步改正 | 原注释还写着「必须写在 pod_target_xcconfig」，与代码矛盾 |

### 历史假设（保留，供对照）

## 六、踩过的坑（同一类错误踩了 3 次，务必先读这节）

### 6.1 CI / 平台

| 坑 | 现象 | 修法 |
|---|---|---|
| `runs-on: macos-26-arm64` 不存在 | job **永久 queued 且不报错**（比失败更难察觉） | 用 `macos-26`（标准 runner 标签不带 `-arm64`） |
| 中文项目路径 | `flutter analyze` 抛 `FormatException`（LSP 的 `Content-Length` 按字节算） | 用 `dart analyze`；CI 路径是 ASCII 不受影响 |
| `.gitignore` 里有 `*.xcodeproj/` | **Xcode 工程没进仓库**，CI 检出后无法构建 | 已移除；`flutter create` 生成的工程必须提交 |
| 本地 `/usr/bin/nm` 是 llvm-nm，CI 上是 GNU nm | GNU nm 对 Mach-O 报 `file format not recognized`，本地绿 CI 红 | 显式探测 `llvm-nm`（含 `/usr/lib/llvm-*/bin`）+ CI 设 `PERCH_REQUIRE_LLVM_NM=1` |
| 单个 `just ci` 步骤 | 失败时只知「有东西坏了」 | 已拆成独立步骤，**失败步骤名即定位** |

### 6.2 Shell（**同一类坑踩了 3 次**）

| 坑 | 说明 |
|---|---|
| `nm ... \| grep -q` | `grep -q` 命中即退出关管道 → `nm` 收 SIGPIPE → `pipefail` 判失败，**匹配成功却报失败** |
| `find ... \| head -1` | 同上，且**掩盖了 C 锚点的真实效果** |
| `grep ... \| head -6` | **第 4 次**。修上一行时紧邻的下一行也是同一个 bug，导致断言步骤 2 秒静默退出、诊断一行没打印，害我以为「注解机制坏了」 |
| 管道吞退出码 | Actions 默认 `bash -e` **不含** `pipefail`，`cmd \| tail` 会让步骤永远绿 |

**纪律**：CI 脚本里每个管道都要显式想一遍退出码；需要"提前退出"的消费者（`grep -q`、`head`）
一律先取全量到变量，或加 `|| true`。

### 6.3 Rust / 构建

| 坑 | 修法 |
|---|---|
| `cargo build --target aarch64-apple-ios` 报 `cc: unrecognized option '-target'`，**但 `.a` 其实已产出** | `perch-ffi` 含 `cdylib`（需链接器），staticlib 不需要。改用 `cargo rustc --crate-type staticlib` |

## 八、怎么继续（给压缩上下文后的自己）

1. **先读本文档**，再看 `docs/09-技术考证报告.md`（那是五个技术问题的权威结论，附出处）
2. 跑一遍 `just ci` 确认基线绿（约 1 分钟）
3. 检查 CI 最新状态，**用 `gh`（已登录，能读日志）**：
   `gh run list --limit 3` → `gh run view <run_id> --log`
   （别用裸 `curl` 打 API：未认证会被限流，且 job 日志接口 403）
4. **不要在看不到日志的情况下反复推 CI 猜测版本** —— 一轮 10 分钟，且证据不足
5. 提交信息写到文件再 `git -c core.quotepath=false commit -q -F /tmp/msgN.txt`（行内 `-m` 带引号会坏）
6. 长 `sleep` 会撞工具 300s 上限 → 单次 `sleep` 不要超过 ~295s

### 常用命令

```bash
just ci          # fmt-check + clippy + 全部测试 + 3 个 iOS target 交叉检查 + iOS 符号断言
just test        # 仅 Rust 测试
just ffi-smoke   # 编 .so 并用 dart:ffi 端到端调用（24 项）
just app-test    # Flutter 单测（13 项，纯 Dart VM）
just app-analyze # 用 dart analyze（不能用 flutter analyze，见 §6.1）
just ios-symbols # 断言 iOS 静态库导出 FFI 符号
```

CI 三点注意：
- runner 用 `macos-26`（**不是** `macos-26-arm64`，那个标签不存在会永久 queued）
- **日志用 `gh run view <id> --log` 读**。裸 `curl` 打 `/actions/jobs/<id>/logs` 会 403；
  `::error::` 注解则只在你真的执行到那一行时才出现，别拿它当兜底
- 公开仓库 macOS runner 免费，但排队可能十几分钟
