# UI 技术栈决策：原生 Swift vs Flutter

> 触发条件：开发机**没有 Mac 且不打算买**（见 `05-云端构建与验证方案.md`），用户提议「实在不行用 Flutter」。
> 本文用实测数据对比，给出建议与 go/no-go 验证方案。**待决策。**

## 一、先纠正一个可能的误解

> **Flutter 不能解决 iOS 的构建问题。**

Flutter 的 iOS 产物**同样必须用 Xcode + macOS 才能编译、签名、上架**。
所以如果你的动机是"用 Flutter 就能在没有 Mac 的情况下做 iOS"——**这条路不通**，iOS 依然要走云端 macOS CI。

**Flutter 真正解决的是另外两件事**：
1. **"看不到效果"**：同一份 Dart 代码可以在本地 **Android 模拟器（本机 `/dev/kvm` 可用 ✓）** 和 Chrome 里跑起来，EPUB 渲染、翻页、高亮**都能在本机看到**。这是当前原生方案最大的痛点。
2. **"多端复用 UI"**：Android / Web / macOS 近乎免费，直接命中项目目标里的"多端复用"。

## 二、实测事实

| **License** | **BSD-3-Clause** ✅ 可自由 fork | ⚠️ **LGPL-3.0**（商业闭源有风险） |
| 依赖面 | 极薄（5 个：platform_interface, wakelock_plus, web, collection, http） | 极薄 |

**结论**：`flutter_readium` 是明显更好的选择（BSD-3 / 更活跃 / 依赖薄）。
它把本项目「一套 API，底层接 Readium Swift + Kotlin + JS」的设计**已经实现好了** —— 而这正是项目目标文档里打算用 UniFFI 手工搭的部分。

**风险**：版本只有 0.6.2、37 stars，是年轻的小团队项目（notalib）。
**但风险可控**：① 底层渲染是**官方 Readium**；② **BSD-3 允许我们 fork 并自己接管**；③ 依赖面极薄，wrapper 本身不大。

## 四、决策其实是两个正交问题

**Q1：UI 技术栈 = 原生 SwiftUI 还是 Flutter？**
**Q2：首发平台 = iOS 还是 Android？**

这两个问题要分开看，而 **Q2 在当前约束下影响巨大**：

> **如果首发 Android，则整条路都不需要 Mac。**
> Android 可以在这台 Linux 上完整构建（APK/AAB）、用模拟器或真机测试、Play Console 是网页版可直接提交上架。
> 而首发 iOS 需要：$99/年开发者账号 + 云端 macOS CI（私有仓库 200 分钟/月，或公开仓库免费）+ 无法真机交互调试。

项目目标文档写的是「iOS 先上线」，但那是在**默认有 Mac** 的前提下写的。
在「没有 Mac 且不买」的现实下，**Android 先行的成本低一个数量级**，而且能更早拿到真实用户、崩溃率、真实性能数据。

## 五、我的建议

**倾向 B（Flutter）+ 认真考虑 Android 先行**，理由：
1. 你的核心约束是"没有 Mac"，而 **Flutter 是唯一能让你在本机看到真实阅读效果的方案**（Android 模拟器有 KVM）；
2. 项目目标的本质是**多端复用**，Flutter 直接命中，而原生方案每加一端都要重写 UI；
3. `flutter_readium` 是 BSD-3 且底层是官方 Readium —— **最难的那部分（EPUB 渲染 + CFI + 高亮）不用自己写，且风险可 fork 兜底**；
4. Rust 核心的设计**完全不变**（Locator / 解析 / 索引 / 同步），已做的工作不浪费，只是绑定层从 UniFFI 换成 `flutter_rust_bridge`。

**但如果你认为「iOS 原生阅读体验 + iOS 用户群」是产品的核心，那 A（原生 Swift）仍然是对的**，
代价是：必须接受"UI 全靠云 CI 盲调"，并且建议在 M2/M6 阶段**租一台云端 Mac**（按小时）来做渲染调试与性能调优。

**不推荐 C**：要写两套 UI，成本高于收益。仅当"只想在本地快速验证核心算法效果"时，可作为一个临时手段。

## 六、go/no-go 验证方案（纯本地，约 1 天）

在**投入 Flutter 之前**，用一个小 spike 一次性消除最大不确定性：

1. 装 Flutter SDK（走 `storage.flutter-io.cn` 镜像）+ 配 `PUB_HOSTED_URL` 到 TUNA
2. `flutter create` 一个空工程，加 `flutter_readium`
3. 起 Android 模拟器（KVM 加速），**导入一本真实的中文 EPUB**
4. 逐项验证（这些是本项目的成败关键）：
   - [ ] 能否正常渲染中文 EPUB（排版、字体、竖排/横排）
   - [ ] 能否翻页 / 滚动，帧率如何（`flutter run --profile` 看帧率）
   - [ ] **能否生成并读取 CFI / Locator**（同步与标注的基础）
   - [ ] **能否做高亮并持久化**（我们的核心功能）
   - [ ] 能否读目录、跳转章节
   - [ ] 打开耗时（目标 <1s）
   - [ ] PDF 用 `pdfrx` 打开是否可用
5. 同一天顺手验证：**iOS 侧能否在云 CI（`macos-26-arm64`）编译通过**（这个可以慢，放 CI 跑）

**判定标准**
- ✅ 全部通过 → Flutter 路线成立，正式立项
- ⚠️ 高亮或 CFI 不可用 → 评估 fork `flutter_readium` 补上的成本
- ❌ 中文排版/渲染质量不可接受 → 退回原生方案（A），并把 Mac 成本纳入预算

## 七、无论选哪个，现在就可以开工的事

**Rust 核心完全不受这个决策影响**：

- `perch-model`（数据模型 / Locator）
- `perch-epub`（容器解析、OPF/NAV、**CFI 生成与解析**）
- `perch-txt`（编码探测、分页、偏移）
- `perch-index`（CJK bigram 分词、倒排）
- `perch-sync`（HLC、合并、冲突检测 + proptest 收敛性测试）

这些占了整个项目**最难的 60~70%**，且**全部能在本机 Linux 上快速开发与测试**。
建议：**不要因为 UI 栈的决策而停工**，先把这部分推起来，同时用 §六 的 spike 定 UI 路线。
