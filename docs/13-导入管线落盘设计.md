# 导入管线落盘设计（Step 2a）

> 用途：把**已经写好、已经有测试**的 `perch_jobs::Pipeline` 接到 FFI 上，让 App 能真正
> 驱动后台精修与索引，并在书架上显示真实进度。
> 状态：**已实现（2026-10-18）**。实现落在 `core/perch-jobs/src/store.rs`（`PathStore`，7 个测试）
> 与 `core/perch-ffi` 的 8 个 `pipeline.*` 方法（4 个测试 + 18 项 Dart 冒烟）。
> 与设计的两处差异，实现时改了：
>
> 1. `StepOutcome::Failed` 的错误信息字段叫 **`reason`**，不叫 `error` ——
>    `{"error": {code, message}}` 是 FFI 的错误通道，业务字段重名会让
>    "这一步失败了"和"这次调用失败了"混在一起（测试第一版就是这么炸的）。
> 2. 句柄表多了一类 `pipeline`，上限 1（`PIPELINE_TOO_MANY_OPEN`），
>    规则补进了 `docs/02` §三点五。
> 前置阅读：`docs/02` §六（三阶段管线）、§三点五（句柄表）、`docs/12` Step 2a。

## 二、关键决策：谁来提供 `BookStore`

`BookStore` 需要四件事：读文件字节、给出格式、写状态、保存产物（索引 + 正文）。

### 选项 A：Dart 侧实现，Rust 回调（C 函数指针 / `NativeCallable`）

- 好处：平台完全掌控存储（将来接 SQLite 自然）。
- 代价：跨语言回调 + 长时阻塞调用 + 错误传播，**全部只能在设备上验**；
  而本项目的基本约束是"能本地验的优先"。回调还会让"崩溃在哪一步"变得难以复现。

### 选项 B（**选定**）：Rust 侧实现 `PathStore`，平台只给路径与目录

- 平台调用 `pipeline.enqueue { book, path, format }` 把"书在哪"告诉 Rust；
  Rust 自己 `std::fs::read` 读文件（**不再走 `bytes_hex`**，10MB 文件省掉 20MB 字符串），
  把产物写进平台给的 `out_dir`。
- 平台读产物更新 UI（标题 / 封面 href / 目录 / 字数 / 状态）。
- 好处：**零回调、纯 Rust、Linux 上能完整验证**（临时目录 + 真实文件即可跑端到端）；
  与 `docs/11` §5.2 ① 的"按路径读"是同一个方向。
- 代价：存储布局暂时由 Rust 决定（见 §四）；将来换 SQLite 时，`PathStore` 换成
  `SqliteStore` 即可，**驱动循环与调度一个字都不用改**。

## 三、FFI 契约草案

```
pipeline.open    { out_dir, policy?, max_chars?, chunk_chars? } -> { handle, resumed }
pipeline.enqueue { handle, book, path, format, state?, priority? } -> { queued, state }
pipeline.step    { handle, now_ms?, gate? } -> { outcome, book?, state?, stats? }
pipeline.status  { handle } -> { idle, pending, running, done, failed, exhausted, next? }
pipeline.promote { handle, book } -> { promoted }        // 用户点开某本书：插队
pipeline.retry   { handle, book } -> { retried }         // 手动重试失败的书
pipeline.cancel  { handle, book } -> { cancelled }       // 删书
pipeline.close   { handle } -> { closed }
```

要点：

1. **`step` 一次只做一个任务**（沿用 `pipeline.rs` 的既有设计）。平台可以在两次
   `step` 之间自由做任何事：进后台、让位给用户阅读、`await` 一个动画。
   这也是"索引任务不许挤掉阅读"在 API 层的体现。
2. `outcome` 复用 `StepOutcome` 的 JSON 形状（`idle` / `refined` / `indexed` /
   `failed` / `exhausted`），**不另立一套**。
3. `now_ms` 由平台传（缺省取 Rust 的 `SystemTime`）：退避重试要看"时间前进"，
   而测试里需要能把时钟捏在手里——`perch-pipeline` 的测试就是这么做的。
4. `gate` 传 `{ allow_any, allow_heavy }`，平台据此注入"是否充电 / 是否 Wi-Fi /
   是否热降级"的判断（`docs/04` #19 未决的那件事，**判断留在平台，规则留在 Rust**）。
5. `pipeline` 是**第三类句柄**（`book` / `txt` / `pipeline`），配额单独计
   （1 个足够，多于 1 个没有意义）。`docs/02` §三点五的表要加一行。

## 四、落盘布局

`out_dir/<bookId>/`：

| 文件 | 内容 | 写法 |
|---|---|---|
| `refinement.json` | `Refinement`（书名/作者/语言/编码/`coverHref`/目录/书脊数/字数） | `serde_json`，小文件 |
| `index.bin` | 倒排索引 | `perch-index` 既有的 delta+varint 格式 |
| `text.json` | `BookText`（正文 + 章节映射） | `serde_json`，v1 接受 ~1.1× 膨胀 |
| `state.json` | `{ state, updated_at_ms }`（`registered` / `refining` / `indexing` / `ready` / `failed`） | Rust 写、Rust 读回来做崩溃恢复 |

**崩溃恢复**：`pipeline.open` 扫 `out_dir/*/state.json`，把没到 `ready` 的书重新入队
（`perch-pipeline` 的恢复能力已经有了，只是没人喂它初始状态）。
`resumed: N` 回报恢复了几本——这个数字要能在书架 UI 上看见。

**明确不做（v1）**：

- **封面字节**：`Refinement` 只带 `coverHref`，不带二进制。抽封面字节需要
  `perch-epub` 再开一个 API，本版**不为了封面开这个口子**——iOS 侧渲染封面走 Readium，
  需要字节时再单独设计（`docs/11` §2.2 已经把"封面字节现在拿不到"记在案）。
- **SQLite**：`docs/04` #3 的方向不变，`PathStore` 是过渡实现。
- **按路径加载已落盘的索引**（`book.load`）：搜索 UI 需要它（避免每次重建索引），
  但它属于 M3，不塞进本步。

## 五、验收标准

| 项 | 怎么验 |
|---|---|
| `PathStore` 的四件事（读 / 格式 / 状态 / 产物） | `perch-jobs` 新增单测，用临时目录 + 真实 EPUB/TXT 夹具 |
| 崩溃恢复 | 单测：写一半状态 → 重新 `open` → 队列里还在、状态不倒退 |
| `pipeline.*` 的 FFI 契约 | `perch-ffi` 单测 + `ffi-smoke` 端到端（真实文件、真步进到 `ready`） |
| 状态与产物落盘 | 端到端断言 `out_dir/<book>/` 下四个文件都在，且 `refinement.json` 内容与 `jobs.refine` 一致 |
| 不回归 | `just ci` 全绿；CI 的模拟器冒烟仍然通过 |

**验收里没有"书架进度条动起来"**——那是 Step 3（UI）的事，本步只保证数据是真的。

## 六、开放问题（不阻塞实现，但要知道）

1. `text.json` 只为了"搜索命中还原 Locator"。若将来搜索改成"重开时按需读正文"，
   这个文件可以省掉。
2. `out_dir` 的清理策略（删书时连带删目录）没有定义——归到"删书"那个 ticket。
3. 平台侧后台队列（`BGProcessingTask`）仍然没做，且**只能在真机/模拟器上验**；
   本步只保证"平台随便什么时候调 `step` 都能正确推进"。
