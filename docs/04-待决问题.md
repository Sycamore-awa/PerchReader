## 🟡 高优先级（M1~M5 之前定）

### 8. 同步后端用哪套？—— ✅ **已决策：CloudKit 私有库，不自建服务器**（2026-10-17 用户拍板）

**策略 v1（四条）**

1. **传输层 = CloudKit 私有数据库**（`CKRecord` + `CKAsset`）。
   **不自建服务器、不自建账号体系**（用 Apple ID）；**只做 Apple 端**（Android 没有官方 CloudKit SDK，将来要跨端再换传输层）。
   - ❌ 作废：自建 Rust API（`axum`）、Supabase、自建 Sign in with Apple。原"建议"整段不再适用。
   - `perch-sync::SyncServer`（纯内存）+ FFI `sync.delta` 的 since 游标 → **降级为测试替身**：
     CloudKit 自带 `CKServerChangeToken` 做增量拉取，自己的游标是重复的。
     `wire` 的 `Change` / `ChangeLog` JSON 形状**继续用**——它变成 CKRecord 的字段序列化。
2. **合并仍在 Rust 设备端**：拉记录 → `sync.merge` → 写回。
   字段级 LWW + HLC **存进记录字段**（每条记录自带字段时间戳），
   **不依赖** CloudKit 自带的整条记录冲突解决（它的粒度是"整条"，会把并发改的两个字段一起丢掉）。
3. **书文件本体走 `CKAsset`**，与元数据放在同一条记录里。
4. **跨设备身份用内容指纹，不用 `BookId`**（⚠️ 见下）。

**⚠️ 由此暴露的一个真问题：`BookId` 不能做跨设备主键**

`BookId` 是本机随机 UUID（`perch-model/src/book.rs`：`BookId::new()` → `Uuid::new_v4()`），
**两台设备导入同一个文件会得到两个不同的 `BookId`**。若同步以 `BookId` 为键，进度与标注会对不上。

跨设备身份必须以 **`Book.fingerprint`** 为准（`perch-import`：`size + 首尾 64KB` 的 SHA-256，
**导入幂等键**，本来就是内容确定的）。
→ 代价：同步落库时 `Locator` / `Annotation` 里绑 `BookId` 的那层要**重映射**。
这是接入 CloudKit 前必须先解决的一件事，见 `docs/02` §八。

**⚠️ 代价（须知）**：私有库占的是**用户自己的 iCloud 空间**（免费档 5GB），
1000 本书很可能超额度。所以**书文件同步必须有开关 + 用量提示**，不能默认静默全量上传。

### 9. 阅读进度的合并语义？—— ⬜ 仍未决（但两种规则都已实现，可切换）
- A. 最后阅读位置（按时间）
- B. 最远阅读位置
- C. **混合（推荐）**：默认最远，但用户显式跳转时采纳该位置
- 这个定义**直接决定"冲突率 <1%"的口径**，必须早定
- **现状**：`perch_sync::ProgressRule` 已把 A（`LastWriteWins`）与 B（`FurthestWins`）都实现成可插拔，
  由调用方选；C（混合）**没有实现**。wire 层（`ChangeLog`）按 HLC 的字段级 LWW 合并。

### 10. TXT 要支持到多大？—— 🔶 代码里已有一个上限，产品口径仍未定
- ≤20MB：全量解码 + 分页缓存
- \>20MB：分片映射 + 块索引表
- 需要知道你实际的场景（会不会有人导入 50MB 的 txt 合集？）
- **现状**：`perch-txt` 是**全量解码**（BOM → 合法 UTF-8 → `chardetng` 猜测），没有"分片映射"；
  `perch-jobs` 的 `ExtractOptions::max_chars` 默认 **5,000,000 字符**，超出即截断并置
  `truncated = true`。所以"单本能吃多大"取决于这个字符上限，而不是文件字节数。
