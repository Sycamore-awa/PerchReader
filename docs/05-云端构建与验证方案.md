# 无 Mac 条件下的构建与验证方案

> 前提变更：**开发机只有 Linux（CachyOS），没有 Mac，且短期内不打算购买。**
> 本文是这套约束下的完整应对方案。所有平台事实均已实测/查证，来源标注在文中。

## 一、先说清楚：没有 Mac 到底不能做什么

这不是"稍微麻烦一点"，而是有几件事**在物理上无法完成**：

| 做不到 | 原因 |
|---|---|
| 跑 Xcode | Xcode 只有 macOS 版 |
| 本地跑 iOS 模拟器 | 依赖 macOS + Xcode |
| 交互式调试（断点、视图层级、Instruments、SwiftUI 预览） | 全部是 Xcode 功能 |
| **在一次操作里**改代码 → 看效果 | 唯一反馈回路是云 CI，每次 10~20 分钟且是异步的 |
| 用 Instruments 量帧率/内存 | 需要 Mac + 真机 |
| 本地构建 `.xcframework` / 签名 / 归档 | 需要 `xcodebuild` |

**这意味着**：SwiftUI/UIKit 的界面开发从"所见即所得"退化成"盲写 → 提交 → 等 CI 报错 → 改"。这是本项目最大的风险，**比任何技术选型都重要**。

## 二、但是：iOS 的"编译—测试—上架"链路可以在云上跑通

### 2.1 GitHub Actions 的 macOS runner（推荐，首选）

**可用镜像与 Xcode 版本（已查证 `actions/runner-images`）**

| 镜像 | 内容 |
|---|---|
| `macos-26-arm64` | macOS 26.x + **Xcode 26.6**（含 iOS 26 SDK） |
| `xcode-27-arm64` | macOS 27.0 / 27.2（Xcode 27.x） |
| `macos-15-arm64` / `macos-14-arm64` | 更旧，用于兼容验证 |

> ⚠️ 上表是 `actions/runner-images` 仓库里的**镜像名**，**不是** YAML 里的 `runs-on` 标签。
> 实际能用的标签是 **`macos-26`**（`macos-latest` / `macos-26-xlarge`）。
> 把 `macos-26-arm64` 写进 `runs-on` 会让 job **永久 queued 且不报错**——这个坑真的踩过，见 §九。

→ 我们计划的 min iOS 18、用 iOS 26 SDK 构建，**完全够用**。

**能做的事**
- `xcodebuild build`（编译，产出真实的编译错误）← **这是最关键的**：哪怕只是让 Swift 代码"编译通过"，也比盲写强太多
- `xcodebuild test`（**在模拟器上跑单元测试与 UI 测试**）
- `xcrun simctl io booted screenshot` → **把界面截图回传成 CI artifact**，你在本地就能看渲染结果（能做像素级/布局检查，甚至历史对比）
- `xcodebuild -create-xcframework`（合成 iOS 用的框架）
- `xcodebuild -exportArchive` + App Store Connect API Key → **上传 TestFlight / 提交审核，不需要 Mac**

**费用（已查证 GitHub 官方定价）**

| 仓库类型 | 费用 |
|---|---|
| **公开仓库** | **免费，额度不限** ✅ 官方原文："usage is free for ... public repositories that use standard GitHub-hosted runners" |
| 私有仓库 | 免费额度 2000 分钟/月；macOS 单价 **$0.062/分钟**（Linux $0.006）≈ **10 倍**，故实际只有 **~200 macOS 分钟/月**；超出 $0.062/分钟 |

> ⚠️ **关键决策点**：这个项目如果走**私有仓库**，每月只有约 200 macOS 分钟 ≈ 13 次 15 分钟的构建。
> 对"没有 Mac、全靠 CI 当编译器和测试机"的开发方式来说，**200 分钟远远不够**。
> → 强烈建议**公开仓库**（或公开一个只用于 CI 的镜像仓库）。这也是本文最重要的建议。

### 2.2 TestFlight（拿到真机数据 / 崩溃率）

- CI 构建 → 上传 App Store Connect → TestFlight → **iPhone 上直接装**（装 TestFlight 不需要 Mac）
- **崩溃率 <0.1%、真实帧率、真实打开耗时** —— 这些只能在真机上量，TestFlight 是唯一不买 Mac 也能走通的路
- 代价：每个 build 处理 + 分发需 10~30 分钟，反馈慢
- 需要：**Apple Developer Program $99/年**（要上架本来就必须有）+ App Store Connect API Key

### 2.3 其他云端 macOS 服务（备选）

| 服务 | 说明 |
|---|---|
| Codemagic / Bitrise / Appcircle | 都有免费额度，iOS 原生构建支持；适合 CI 分钟数不够时的补充 |
| Xcode Cloud（Apple 官方） | 需 $99/年开发者账号，按分钟计费，与 TestFlight/App Store Connect 集成最顺 |
| MacinCloud / MacStadium（租用 Mac） | 按小时/月租远程 Mac，能拿到**交互式 Xcode**（即恢复"改代码→看效果"的回路）。这是最能解决根本问题的办法，但要花钱 |

## 三、本地能做的加速手段

### 3.1 Linux 上的 Swift 工具链（可选，但值得）

AUR 有 `swift-bin`（约 2GB）。装了之后可以在 Linux 上：
- ✅ **类型检查纯 Swift 代码**（不依赖 UIKit/SwiftUI 的部分）：Locator 适配层、FFI 桥接层、同步客户端逻辑、数据模型、算法
- ✅ 跑这些逻辑的单元测试
- ❌ 不能编译任何 `import UIKit` / `import SwiftUI` 的代码

**价值**：把 Swift 侧的"非 UI 逻辑"纳入本地快速回路，能让 UI 层在 CI 里要修的错少一大半。
**建议**：M0 之后装上（如果 AUR 构建顺利）。

### 3.2 本地 Rust 侧（已就绪）

- `cargo test` 全量核心测试（宿主）
- `cargo check --target aarch64-apple-ios` 提前发现 iOS 侧的编译问题
- `cargo rustc -p perch-ffi --target aarch64-apple-ios --crate-type staticlib` 产出静态库（**实测可产出真 Mach-O arm64 `.a`**）
- `just ios-symbols` 用 `llvm-nm` 断言 `_perch_call` / `_perch_string_free` 是全局导出符号
- `just ffi-smoke` 用 `dart:ffi` 加载 `.so` 端到端调用（55 项）

> ⚠️ 原文最后一条是"`uniffi-bindgen` 生成 Swift 绑定（**实测可在 Linux 完成**）"。
> 这条**能力上成立但不是当前方案**：绑定层已改为手写 C ABI + JSON（见 `docs/10` §三），
> 仓库里没有 UniFFI 绑定。

## 四、实际的 CI 结构（2026-10-17 按 `.github/workflows/ci.yml` 核对）

**三个 job**（原文写"两个 job"并给了 XcodeGen + bindgen-drift 的示意 yaml，**都未采用**）：

| job | runner | 做什么 |
|---|---|---|
| `core-linux` | `ubuntu-latest` | 装 rustup（`--default-toolchain none`，工具链与 3 个 iOS target 由 `core/rust-toolchain.toml` 自动补齐）→ 装 `just` → 确保 `llvm-nm` → 拆成独立步骤跑 `just fmt-check` / `just lint` / `just test` / `just check-ios` / `just check-ios-sim` / `just ios-symbols` |
| `ffi-smoke` | `ubuntu-latest` | 装 rustup + Dart SDK（官方 tarball）→ `cargo build -p perch-ffi --release` → 在 `dart/perch_core` 跑 `dart run tool/ffi_smoke.dart`（55 项，真实加载 `.so`） |
| `ios-macos` | **`macos-26`** | `needs: core-linux`。诊断环境 → 装 rustup（**必须 `--default-toolchain stable`**，不能是 `none`）→ 装 Flutter → `flutter pub get` → `dart analyze` → `flutter test` → `flutter build ios --simulator` → `if: always()` 诊断 → **断言 Rust 符号已链入 app bundle** → 汇总 |

**设计要点**
- `check-ios` 放在 **Linux job** 里 —— 它便宜，能在 1~2 分钟内挡掉大部分"iOS 编译失败"，不用浪费宝贵的 macOS 分钟
- **没有"绑定漂移检查"**：绑定层是手写 C ABI，不存在生成物；对应位置换成了 `just ios-symbols`（静态库符号导出）与 `ffi-smoke`（Rust ↔ Dart 契约端到端）
- **没有 XcodeGen**：iOS 工程是 `flutter create` 生成并提交的 `app/ios/Runner.xcodeproj`，CI 直接 `flutter build`
- 符号断言遍历 app bundle 里**所有** Mach-O（不是只看 `Runner`），任一镜像里同时出现 `_perch_call` 与 `_perch_string_free` 即通过（原因见 `docs/10` §四 第 19 轮）
- 截图 artifact（原方案里的视觉反馈）**尚未做**，属未覆盖项，见 §九

## 五、这套约束下必须调整的开发策略

### 5.1 把"可本地验证"的部分做到极致

原里程碑拆解里已经标注了每项的"验证位置"。**执行顺序要据此重排**：

```
优先做（Linux 全可验，占 60~70% 工程量）
  ├─ perchep-model：数据模型、Locator 设计
  ├─ perch-epub：容器解析、OPF/NAV、CFI 生成与解析   ← 阅读器正确性的核心
  ├─ perch-txt：编码探测、分页算法、偏移换算          ← 中文阅读的核心
  ├─ perch-index：CJK bigram 分词、倒排、前缀
  ├─ perch-sync：HLC、合并、冲突检测 + proptest 收敛性测试  ← "同步准"的全部保证
  └─ perch-ffi：手写 C ABI + JSON 契约（原写 "UniFFI 契约（含 Swift 绑定生成）"，已不适用）
        ↓ 以上全部在本地快速迭代，无需 Mac

后做（必须云端 / 必须真机）
  ├─ SwiftUI 界面（盲写 → CI 编译 → 截图检查）
  ├─ Readium 集成与 EPUB 渲染
  ├─ 帧率 / 内存 / 打开耗时优化   ← 依赖真机
  └─ 崩溃率（MetricKit via TestFlight）  ← 依赖真机 + 用户量
```

### 5.2 关于质量目标：必须诚实调整预期

| 目标 | 无 Mac 能否达成 | 说明 |
|---|---|---|
| 导入快（1000 本 <10s） | ✅ 可以 | 主要是算法 + I/O，Linux 可基准测试 |
| 同步准（冲突率 <1%） | ✅ 可以 | 合并引擎纯逻辑，Linux 可随机化验证 |
| 阅读稳（打开 <1s / 60fps） | ⚠️ 部分 | 算法层可测；**渲染层性能优化几乎无法迭代** —— 只能靠"预防性设计"（约束 DOM 大小、不重建 WebView 等）+ 上线后数据 |
| 崩溃率 <0.1% | ⚠️ 慢 | 能通过 TestFlight + MetricKit 度量，但每个修复周期很长 |

**结论**：**第一个 iOS 版本应当是"工程正确、体验够用"，而不是"打磨到极致"。**
真正的性能/手感打磨（仿真翻页、60fps 调优、崩溃率收敛）建议放在"能拿到一台 Mac（哪怕是租的 / 借的）"之后集中做。否则会在 CI 的 10~20 分钟回路里消耗掉大量时间。

### 5.3 备选方案：先做一个本地能跑的"开发用外壳" —— 🔶 已由 Flutter 的 web 目标覆盖

如果希望**尽快在本地看到阅读效果**（而不是每改一行等 15 分钟 CI），可以：

- 用 **Tauri 2 + Web 前端**（或纯 Web + WASM）做一个**仅用于开发的壳**，把同一套 Rust 核心编成 WASM 跑起来
- 好处：本地立即看到 EPUB/TXT 渲染、翻页、标注、搜索的实际效果；核心逻辑的验证回路从 15 分钟降到 1 秒
- 代价：额外工作量（约 1~2 周）；且它**不是产品**，UI 不能复用（项目目标也明确说桌面不用它统一移动端 UI）
- 判断：**如果能接受额外投入，这个"开发壳"能显著降低整个项目的风险**，因为它把"看不到效果"这个最大问题解决了。是否要做，需要你决策。

> **更新（2026-10-17）**：UI 栈定为 Flutter 后，**Flutter 自带 web 目标**，
> `just app-web` / `just app-headless-check` 就是本地预览回路（`app/web/readiumReader.js` 已在仓库里）。
> 因此**不再单独做 Tauri/WASM 壳**。注意 web 阅读页仍有一个未验证的 `manifest.json` 问题（`docs/07` §三）。

## 九、CI 已跑通（2026-10-17 实测）

GitHub Actions **三个 job 全部通过**（原文写"两次 job"——后来加了 `ffi-smoke`），
**这是项目第一次在真实 macOS + Xcode 上把 Flutter + flutter_readium 编进 iOS App**。

| Job | runner | 结果 | 耗时 |
|---|---|---|---|
| Rust 核心（fmt / clippy / 测试 / iOS 交叉编译 / 符号断言） | `ubuntu-latest` | ✅ success | ~2 min |
| FFI 端到端（Dart ↔ Rust C ABI） | `ubuntu-latest` | ✅ success | ~2~3 min |
| iOS 编译（模拟器）+ 符号断言 | **`macos-26`** | ✅ success | **7 min 25 s** |

`ios-macos` 的 12 个步骤全部真实执行（无跳过）：诊断环境 → 安装 rustup（`--default-toolchain stable`）
→ 确认 cargo 可用 → 安装 Flutter → pub get → `dart analyze` → `flutter test` →
**`flutter build ios --simulator`** → `if: always()` 诊断 → **断言 Rust 符号已链入 app bundle** → 汇总。

> 符号断言的最终结果：`_perch_call` / `_perch_string_free` 在 **`Runner.app/Runner.debug.dylib`** 里，
> 而 `perch_core_ffi.framework` 里只有 `PerchCoreFfiPlugin` 的 Swift 符号（结构见 `docs/10` §四 第 20 轮）。

### ⚠️ 踩到的坑（值得单独记）

**`runs-on: macos-26-arm64` 这个标签不存在，会让 job 永久 `queued` 且不报错。**

最初我按 `actions/runner-images` 仓库里的**镜像文件名**（`macos-26-arm64-Readme.md`）
当成了 YAML 标签，结果 job 一直排队、`started_at` 有值却没有任何 step 开始 ——
这种"假排队"比失败更难察觉，因为界面不报错。

官方标签表（macOS 26）：

| 镜像 | YAML 标签 |
|---|---|
| macOS 26 Arm64 | **`macos-26`** / `macos-latest` / `macos-26-xlarge` |
| macOS 26（Intel） | `macos-latest-large` / `macos-26-intel` / `macos-26-large` |

标准 runner 的标签**不带 `-arm64` 后缀**；`macos-26` 本身就是 arm64 镜像。

**排查方法**：job 状态长期 `queued` 且没有任何 step 进入 `in_progress`，
几乎一定是 `runs-on` 标签写错。查 `actions/runner-images` 根目录 README 的标签表核对。

### 目前 CI 覆盖到什么、没覆盖到什么

✅ **已覆盖**
- Rust 核心：在全新 Ubuntu 上从零装 rustup（`--default-toolchain none`）→
  由 `core/rust-toolchain.toml` 自动补齐工具链与 3 个 iOS target → **421 个测试** + clippy
  （原文写 190 个测试，已过时）
- Rust ↔ Dart 契约：`ffi-smoke` 用 `dart:ffi` 真实加载 `.so` 调用 **55 项**
- iOS：Flutter 依赖解析、`dart analyze`、`flutter test`（13 项）、**模拟器构建成功**（免签名）、
  **Rust 符号确实在 app bundle 里**

❌ **尚未覆盖**
- **模拟器上真正运行**（`xcrun simctl` 启动 App + 截图；`flutter test` 是纯 Dart VM，不启动 App）
- 真机 / 归档 / TestFlight 上传（需要签名证书与 App Store Connect API Key）
- 性能与崩溃率（需要真机与样本量）
- 运行时 `DynamicLibrary.process()` 是否真的解析得到符号（需要真的把 App 跑起来）

把"能编译 + 符号在"升级成"能跑"，是下一个 CI 里程碑。
