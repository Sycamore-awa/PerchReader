## 三、三个断点：「文档说完成」与「真能用」之间的缝

### 3.1 App 运行时不调用 Rust 核心

`app/lib/*.dart` 里**没有** `import 'package:perch_core/...'`——FFI 只在 CI 的符号断言与 Dart 冒烟里被验证过。

- 「符号在 bundle 里」（`nm` 断言）≠「`DynamicLibrary.process()` 运行时解析得到」（需要进程真的跑起来）。
- 推论：**即使现在把 App 跑在模拟器上，也验证不到 FFI**。所以 Step 1 必须包含"让 App 真的调用核心"。

### 3.2 核心能力大面积够不到 App

`perch_call` 目前 12 个方法（`version` / `locator.validate` / `fingerprint` / `jobs.refine` / `pdf.analyze` /
`txt.analyze` / `index.search` / `book.open|search|close` / `hlc.parse` / `sync.merge` / `sync.delta`）。

缺两类入口：

- **`perch-jobs` / `perch-pipeline`**：整套后台精修与索引逻辑在 Rust 里已完成，但 App 驱动不了它
  → 书架上的「正在精修 N 本」只能接假数据。
- **TXT 阅读路径**（`docs/11` §5.2 ①）：`txt.analyze` 要 `bytes_hex` 且把全文当 JSON 吐回，
  10 MB 文件 = 20 MB 十六进制字符串。阅读路径必须走句柄化的 `txt.open` / `txt.slice`。

### 3.3 同步缺前置

- CloudKit 传输层**一行没写**（决策已定，见 `docs/04` #8）。
- 更前置的问题：`BookId` 是本机随机 UUID，跨设备主键必须换成 `Book.fingerprint`，
  否则两台设备导入同一本书对不上（`docs/02` §八点二）。

#### CI 实跑记录（2026-10-18，每一次都是"步骤自己把问题说出来"）

**第 1 次（run 39086024546）**

```
✓ Rust 核心 / FFI 端到端 / Flutter 单测 / 编译 iOS / 符号断言    全部通过
✗ 模拟器冒烟: line 79: console_log<乱码>: unbound variable
```

根因：macOS 自带 `/bin/bash` 是 **3.2**，不是 UTF-8 感知的。脚本里
`echo "… → $console_log）----"` 的变量名后面紧跟**全角括号**，bash 3.2 把中文字节
算进了变量名。Linux 的 bash 5 不会这样 —— 所以本地 harness（也是 bash 5）全绿也拦不住，
这是「本地绿 ≠ CI 绿」的又一例。

已修：3 处写成 `${var}`；去掉 `${x%%$'\n'*}` 这种依赖 `$'…'` 在参数展开里的写法。
防复发：`core-linux` 加了静态检查 `grep -P '\$[A-Za-z_][A-Za-z0-9_]*(?=[^\x00-\x7F])'`，
harness 里也有一份；本地用「把 bug 注回去」验证过它真的会拦。

**第 2 次（run 39087225370）：目标其实达成了，失败的是断言通道**

```
✗ 模拟器冒烟：控制台里没有 [perch-selfcheck]（等了 120s）
  但 ② 兜底：系统日志里找到 →
  Runner: (Flutter) flutter: [perch-selfcheck] ok core=0.1.0
```

**也就是说：App 真的在 iOS 模拟器上跑起来了，`DynamicLibrary.process()` 在运行时
解析到了 Rust 符号。** 截图 artifact 里能直接看到书库页和标题栏的 `core 0.1.0` 角标
（`home.png`，1206×2622）。

两个问题，都是"观察手段"的问题，不是产品代码的问题：

| 问题 | 根因 | 修法 |
|---|---|---|
| 断言查错了通道 | Flutter 的 `print`/`debugPrint` 走 **os_log**，`simctl launch --console-pty` 只拿得到 NSLog/stderr | 主通道改成 `log show` **轮询**（每次新进程、直接读日志库，不受 stdout 缓冲影响）；控制台降为旁证 |
| 失败路径会**死循环** | 我写的 `run_with_timeout` 没声明 `local`，函数内的 `waited` 把外层轮询的 `waited` 覆盖掉，外层 `while` 计数永远涨不上去 | helper 内全部 `local`；外层计数改名 `waited_s`；harness 里给内层脚本套 `timeout 120`，死循环直接以 124 失败 |

> 第二个问题是**本地 harness 抓到的**（它自己挂到工具 300s 上限），这就是
> Step 1c 存在的意义：CI 脚本的 bug 不该用一轮 15 分钟的云 CI 去发现。

## 六、纪律（与 `docs/10` §六重复，但值得再写一遍）

1. **没有日志就不要改代码**——先 `gh auth status` / `gh run view --log`。
2. **断言前先枚举**：别写死某个文件名（`nm Runner` 的教训）。
3. **CI 脚本里每个管道都要想一遍退出码**：`grep -q` / `head` 会引发 SIGPIPE，
   在 `pipefail` 下让失败变成哑巴（同类坑已 4 次）。
4. **改实现就顺手改矛盾的旧注释**，数字要现算。
5. **本地绿 ≠ CI 绿**：平台差异要单独想一遍（macOS 的 bash 是 **3.2**、不是 UTF-8 感知、
   没有 GNU `timeout`；Linux 上这些都不会暴露）。凡涉及版本/编码的假设，要么在 CI 上验，
   要么写成静态检查挡住（例如变量名相邻非 ASCII 那条）。
